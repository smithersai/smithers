Jev Harness: Engineering

Draft 1, 2026-09-17. How the design doc gets built: what is new, what is reused, in what order, how it is tested, and what can go wrong. The build breakdown and the monitoring plan are separate steps after this doc is approved.

Summary. One new package, @smthrs/opencode, serves OpenCode protocol v2 over the existing Agent.run stream on the existing durable engine. One new core module, Classifier in @smthrs/model, wraps Jev behind an Effect service. One new flow source, StandardFlows.classify, gives cells the door. Health is a projection inside the server package. Nothing in apps/ changes. The walking skeleton is health, session create, prompt, and a streamed text answer; everything after that is a projection or a binding.

Decision 2026-09-17, after phase 1. Protocol v1 (see the design doc section 6). Composition facts proven by the spike in composition-brief.md: one Agent.run per prompt inside a registered flow, caller-chosen execution ids, permission park and same-id resume, in-memory steering, interrupt through engine.interrupt with the projection closed from the body's exit (no Aborted event reaches the consumer), the capability envelope must be declared, the server must process.chdir into the directory, and Node runtime with the undici client. Package and CLI plumbing is in scaffold-brief.md. The OpenAI key in this shell has no credits; the working seat is cerebras:gpt-oss-120b. Phases S1 to S3 are re-cut: S1 = package, v1 routes, store, SSE, projection over a scripted driver, CLI verb, proven against the hosted app with the trace driver; S2 = the real engine driver with permissions, steering, interrupt, and resume, proven live on Cerebras; S3 = classify flows wired in, health, cost, docs.

1. Principles

  • Walking skeleton first. The hosted app must show a streamed answer from the real cell loop before any tool card, permission, classifier, or dot exists.
  • Transcribe, do not import. OpenCode's protocol is Effect 4 beta 83 with identity-keyed schemas; we are on rc.115. We copy the endpoint and schema shapes we need into our package as our own Effect Schema and check them against OpenCode's OpenAPI and protocol sources in a contract test. No @opencode-ai/* runtime dependency in the server; the typed clients are dev dependencies for tests only.
  • One loop. The server is an adapter over Agent.run, the same as AgentSession and AgentAction. It never reimplements a frame.
  • Jev is advisory. Health never blocks a run; classify answers are data the cell branches on; permissions and completion stay with the harness and the person.
  • Least code. Reuse FlowEngine and the SQLite engine store from NodeControl, the Jev wire client from apps/server/src/jev.ts (copied into the Effect module, then the old sites migrate later), StandardFlows for capabilities, and OpenCode's app and typed clients for UI and tests.

4. Component design

4.1 Runs: one Agent.run per prompt

  • A session is a directory plus a lineage id. A prompt on an idle session starts a flow execution whose body is Agent.run with session = sessionID, prompt = conversation tail + new text, the seat from the session's model, flows = [filesystem, shell, tests, clock, approval, classify], limits from the CLI, readOnlyCap armed, approvalChannel = true.
  • A prompt on a busy session goes into the session's Steering.Source (the in-memory queue the harness drains at frame boundaries) and is also stored so a restart re-queues it.
  • The execution id is the assistant message id, so the journal and the timeline share one key.
  • Permission: the authorize hook registers a pending per_… request and fails with Permission.PermissionRequired before the boundary opens, the same shape AgentSession uses. The reply installs a grant in a per-session grant table, then re-drives the parked execution. always stores a rule for the flow and pattern; reject resolves the call as permission_denied.
  • Interrupt is fiber interruption; the stream's Aborted event closes the projection.
  • Restart: on boot, every session with a parked or running execution is re-driven from the engine; the projection replays journaled agent events into the message store so nothing renders twice (events carry the execution's ordinal as their idempotency key).

4.2 Projection: AgentEvent to OpenCode

  • A pure fold: (state, AgentEvent) → (state, OpenCodeEvent[]), table in the design doc section 6.1. Tested with recorded event fixtures from a real run.
  • Ids: msg_ per assistant message, one per prompt; tool item ids prt_ derived from the call identity (session/frame/cell/ordinal) so a replayed call maps to the same item.
  • The message store persists the folded messages so GET /api/session/:id/message is a read, not a replay.
  • SSE hub: a broadcast per directory with a bounded replay buffer; a late subscriber gets server.connected and then live events; the app reloads history over HTTP on connect, so the buffer only covers reconnects.

4.3 Health

  • Declared as a curated classifier harness/health with the state and questions from the design doc section 3.
  • Triggered on CellSettled; runs on its own fiber with a 1.5 s deadline; folds its answer into the session's health state; emits session.renamed and a health item only when the color changes.
  • State inputs come from the projection's own fold (frames since edit from MutationObserved, demands, last calls, last prints), so health reads no engine internals.

4.4 Classifier and Evaluator

  • Evaluator.layerVercelGateway is the Node and Worker safe transport: HttpClient from the kernel, one POST, a deadline, no retries (the caller decides), zero data retention on by default.
  • Classifier.evaluateAll fans out with Effect.forEach({ concurrency }); each state is its own request because Jev takes one state per call.
  • Answer decoding: the transport returns raw answers; Classifier decodes them with the schema derived from the questions and fails typed invalid_answer on a mismatch.
  • Later, not now: migrate apps/server/src/jev.ts and JevSessionChecker.ts onto the module.

9. Monitoring hooks to build in

Placeholders the monitoring plan will fill: smithers opencode --trace writes every request, event, and Jev call to .smithers/opencode-trace.ndjson; the run summary lists frames, calls, classify calls, Jev latency, and spend; health decisions are journaled as flows.opencode.health.v1 records so agreement can be scored after the day.
