Each deployment stage keeps its Alchemy state in its own R2 object, `alchemy/SmithersBuildRemoteCache/<stage>.json`, with its own lock, and its own local working copy, `.alchemy/state/SmithersBuildRemoteCache/<stage>`. Deploying one stage no longer locks, pulls, or republishes another. `pnpm run migrate-state` splits the old shared object into per-stage objects under the old lock: it copies the shared object byte for byte to `alchemy/SmithersBuildRemoteCache.pre-split.json`, writes the stage objects, reads every copy back, and only then replaces the shared object with a marker that older wrappers refuse. It refuses while the local stack state directory holds unpublished state from the shared layout. `-- --dry-run` previews it and writes nothing, a second run is a no-op, and `pnpm run restore-shared-state` reverses it from the backup. A deployment fails closed, naming that command, while the shared object still holds state. A stage directory spelled like an existing one in another case is reported as such, not as a symbolic link. `DeployOptions.remoteState` is now `stateBucket`, and `remoteStateFromEnvironment` is now `stateBucketFromEnvironment`; the deploy wrapper chooses the key from the stage.
