```text
smithers-ci [command] [flags]
```

Run it with `bunx smithers-ci` in any directory of a Git repository. It works on
the whole repository: the root is the repository's top directory, found from
the directory you run it in.
A partial clone (`--filter`) and a shallow clone (`--depth`) work too: the
replay fetches what a partial clone lacks from its remote, and replays the
commits a shallow clone holds.

The four tables on this page are checked against the command surface in
`src/contract/Command.ts` by `test/docs.test.ts`: a command, flag, default or
exit code or variable that one has and the other lacks fails the package's tests.

## Commands

| Command                 | What it does                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `smithers-ci`           | Measure today's CI, replay past commits, and print the speedup. Writes nothing to the repository. |
| `smithers-ci apply`     | Write the Smithers workspace, target files and CI workflow the report was measured with.          |
| `smithers-ci inventory` | Print what the repository's CI does today.                                                        |
| `smithers-ci replay`    | Replay past commits and print the replay report.                                                  |

`apply` is the only command that changes the repository. It checks every path
before it writes any, so a refusal (exit `3`) leaves nothing written. It
refuses, and names the path, when:

- a file it would replace is not one `smithers-ci` generated. A generated file
  starts with `Generated by smithers-ci.` in a comment;
- a build file of your own is where Smithers build would read it beside the
  generated ones: a root `PACKAGE.ts` or `PACKAGE.vibe`, or
  `.smithers/WORKSPACE.ts`;
- a link in the path leads outside the repository, or to nothing;
- a file is where a directory must go, or a directory where the file must go;
- a Smithers workspace `smithers-ci` did not write is there: `WORKSPACE.ts`,
  `.smithers/WORKSPACE.ts` or `.smithers/WORKSPACE.smithers`. `apply` leaves
  it alone and says how to go on:

```text
smithers-ci: inventory: .smithers/WORKSPACE.smithers was not written by smithers-ci, so apply leaves it alone: run this repository's Smithers build with smthrs ci, or remove .smithers/WORKSPACE.smithers to have apply write its files
```

`apply` writes those files and nothing else. It adds no line to your
`.gitignore`: the cache is never in your checkout (see
[Where the cache is on a machine](../concepts/cache.md#where-the-cache-is-on-a-machine)).

Every file it writes is under `.smithers/`, except the workflow, whose place
GitHub fixes. [Make it your CI](../getting-started/quickstart.md#make-it-your-ci)
lists them. An earlier `smithers-ci` wrote a `PACKAGE.ts` at the repository's
root, `.smithers/WORKSPACE.ts`, `.smithers/ci-targets.json` and
`.smithers/ci/NOT-REPRODUCED.md`. `apply` removes each of those that
`smithers-ci` generated, and prints `removed` and the path: what they held is
in the files it writes now. A second `apply` writes the same bytes.

`apply --check` writes nothing. It works out the same files `apply` would
write, from the same repository, and compares them byte for byte with the
files there. It prints one line for each file `apply` would change and exits
`1`:

```text
.smithers/WORKSPACE.smithers is out of date: run smithers-ci apply
.smithers/ci/legs.txt is missing: run smithers-ci apply
PACKAGE.ts is no longer used: run smithers-ci apply
```

When nothing would change, it prints
`smithers-ci: the generated files are up to date` and exits `0`. It refuses
what `apply` refuses, with the same line and exit `3`. Give it the `--cache`
URL you gave `apply`: the workflow holds that URL, so the files differ without
it. The workflow `apply` writes runs this check as its first step; see
[When your repository changes](../getting-started/quickstart.md#when-your-repository-changes).

## Flags

| Flag               | Commands                                                     | Default  | What it does                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--commits`        | `smithers-ci`, `smithers-ci replay`                          | `20`     | How many past commits to replay.                                                                                                                                          |
| `--mode`           | `smithers-ci`, `smithers-ci replay`                          | `normal` | normal, fast, or both.                                                                                                                                                    |
| `--jobs`           | `smithers-ci`, `smithers-ci replay`                          | none     | Most jobs to run at once, in the baseline and in each mode; the default is this machine's core count divided by 4, at least 1, as a GitHub runner gives each job 4 cores. |
| `--cache`          | `smithers-ci`, `smithers-ci replay`, `smithers-ci apply`     | none     | URL of a shared cache, with no user name or password; its token is read from SMITHERS_CACHE_TOKEN.                                                                        |
| `--targets`        | `smithers-ci`, `smithers-ci replay`                          | none     | Smithers build patterns to replay, separated by commas, on a repository that already builds with Smithers build; the default is what its CI runs.                         |
| `--no-trial`       | `smithers-ci`, `smithers-ci replay`                          | `false`  | Replay every job, without first running the CI once to leave out the jobs that fail on this machine.                                                                      |
| `--no-apply-check` | `smithers-ci`, `smithers-ci replay`                          | `false`  | Skip the run of the newest commit with the files apply writes committed, which finds a step that fails over one of them.                                                  |
| `--cold`           | `smithers-ci`, `smithers-ci replay`                          | `false`  | Count from an empty cache: skip the run before the first counted commit that fills the caches a CI run finds.                                                             |
| `--reruns`         | `smithers-ci`, `smithers-ci replay`                          | `1`      | How many times a failed step runs again to tell a flaky failure from a broken one; 0 turns it off.                                                                        |
| `--stall-minutes`  | `smithers-ci`, `smithers-ci replay`                          | `10`     | Stop a step whose processes use no CPU and print nothing for this many minutes; it counts as failed.                                                                      |
| `--out`            | `smithers-ci`, `smithers-ci replay`                          | none     | Also write the report as an HTML file here.                                                                                                                               |
| `--json`           | `smithers-ci`, `smithers-ci inventory`, `smithers-ci replay` | `false`  | Print the document as JSON.                                                                                                                                               |
| `--allow-root`     | `smithers-ci`, `smithers-ci replay`                          | `false`  | Replay even when run as root, where a past commit's commands could change this machine.                                                                                   |
| `--check`          | `smithers-ci apply`                                          | `false`  | Write nothing; name each file apply would change, and exit 1 if there is one.                                                                                             |
| `--allow-docker`   | `smithers-ci`, `smithers-ci replay`, `smithers-ci apply`     | `false`  | Take the jobs that run docker or podman too, and let a replayed step reach a container daemon, which can read and write every file of this machine.                       |

A flag's value is the next argument, as in `--commits 5`. `--no-trial`, `--no-apply-check`, `--cold`, `--json`, `--allow-root`, `--check` and `--allow-docker` take no value.
`--help` and `-h` are accepted on every command and print its commands and flags.

Of the commits `--commits` counts, one that had no CI the program can run is not
replayed; the report lists it with the reason.

`--mode fast` and `--mode both` add fast mode to the replay; see
[Normal mode and fast mode](../concepts/modes.md). `--cache` is described in
[The cache](../concepts/cache.md); a URL with a user name or a
password in it is a usage error (exit `2`), because `apply` writes the URL into
the workflow. With `--json`, `inventory` prints the inventory and the other two
commands print the replay report.

Without `--allow-docker`, a job with a step that runs `docker`,
`docker compose`, `docker-compose`, `podman` or `nerdctl` is not replayed,
`apply` writes no target for it, and no replayed step reaches a container
daemon. The report lists the job with what it runs and this flag. With the flag
those jobs are replayed and applied, and their steps reach your daemon. A
daemon does what it is asked with every file of this machine, whatever else a
step is kept from, so give the flag only for a history you trust. See
[What a step can reach](../concepts/how-it-works.md#what-a-step-can-reach).

### The first run

A CI run starts with what the run before it left. So before the first counted
commit, the baseline, normal mode and fast mode each run once at the commit
before the oldest replayed one, each in a home of its own. That run fills what
the way keeps from one commit to the next: its cache of results and what its
jobs save with `actions/cache`. It is in no commit's
time and not in the speedup. The report gives its time in each way on one line
(`firstRun` under `--json`):

```text
the first run, with an empty cache, took 4m 10s as the baseline and 5m 02s in normal mode; it happens once and is in none of these times
```

A step that fails in a mode's first run stops nothing: the cache holds what
passed. `--cold` skips the first run and counts from an empty cache. When no
commit comes before the oldest replayed one, or that commit has no CI that runs
on this machine, the replay starts with an empty cache and the report says so
(`cold` under `--json`). On a repository with
[its own targets](../concepts/own-targets.md), the same holds.

### A short CI

Smithers CI starts once for each commit. When normal mode took longer than your
CI and that start is more than a twentieth of your CI's time for a commit, the
report gives both times on one line (`startCost` under `--json`, with
`commitMs` and `startMs`):

```text
your CI takes 5.8s for a commit and Smithers CI takes 3.2s to start, so only a commit that reuses results is faster here
```

Both times are a mean over the commits the speedup covers. The speedup and
every wall time still count each start.

### Jobs that cannot pass here

The baseline's first run finds the jobs that cannot pass on this machine. A job
that fails it runs once more, at the newest commit, in a home no counted run
reads. One that passes there was flaky, or broken at that one commit, and is
replayed. One that fails again is not replayed at any commit: the report lists it
as failing on this machine with the step that failed, its exit code, the first
line of its error and the commits it failed at (`fails-here` under `--json`), and
says the same of every job that needs it. For a matrix job this holds per variant.
On a repository with [its own targets](../concepts/own-targets.md), the same
holds for each target.

A step that starts a program whose file asks for rights, as `/usr/bin/ping` asks
for `cap_net_raw`, gets none of them in the replay's jail and fails, where a
runner gives them. When a run of `smthrs ci` names such a program, its job, or
its matrix variant, is not replayed from that commit on, and the report lists it
as failing on this machine: ``runs `ping`, which needs rights this machine's jail
takes away``. That commit runs again without it, in every way, and earlier
commits keep their numbers. `apply` still writes the job.

`fails-here` means the job did not pass on this machine in two runs, and so is
compared in no way: it says nothing of whether Smithers CI runs that job right.
The speedup always says how many jobs it covers, such as `over 3 of 5 jobs`
(`jobs` under `--json`). When half or more of the jobs that could run here are
left out, the program prints no report: standard error lists each of them with
why, and it exits `3`.

With `--cold`, or when there is no commit to run first, the baseline runs once
more for this, at the oldest replayed commit, in a home of its own. A line gives
the time that run took, which is in no other number.

A job that passes the first run and fails at a later commit is a failed baseline
at that commit. `smithers-ci apply` writes every job, those left out here too:
they pass on your runners. `--no-trial` leaves no job out: it runs every job at
every commit, in the baseline and in each mode, and compares them all.

### Steps that fail

A step that fails runs once more, in the baseline and in each mode. When it
passes then, it is `flaky`; when it fails again, it failed. `--reruns` sets how
many times it runs again, and `--reruns 0` turns that off. A step that fails
with the exit code and the first line of error it failed with at the commit
before, or in the first run, is not run again: twice the same is broken, not
flaky. No such run is in a commit's time or in the speedup. The report says how
many there were and what they took (`reruns` under `--json`):

```text
2 failed steps ran again, which took 50m 10s and is in none of these times
```

### CPU time

The report gives the CPU time each way's steps used beside its wall time, on
one line, and for each commit and way under `--json` (`cpuMs`; `baselineCpuMs`,
`normalCpuMs` and `fastCpuMs` over the commits the wall times cover):

```text
the steps used 26m 10s of CPU time as the baseline and 4m 02s in normal mode (6.5× less)
```

It is read from each step's processes while the step runs: four times a second
on Linux, every two seconds on macOS. A machine whose processes cannot be read
gives a report with no CPU time.

### Steps that stop making progress

A step whose whole process tree uses less than one hundredth of a CPU core and
prints nothing for `--stall-minutes` is stopped and fails with `it made no
progress for 10 minutes`, in the baseline and in every mode. It is not run again.
A step that waits that long on purpose, such as a test that sleeps, needs a
higher limit. The value may be a fraction. A value that is not above 0 is a usage
error (exit `2`). The program reads CPU time from `/proc` on Linux and from `ps`
on macOS; when it cannot read them, it stops no step this way. The limit of six
hours for one step still applies.

### Fast mode and its model

Fast mode needs the model that predicts which tests a change cannot break.
`--mode fast` and `--mode both` ask it one small question before anything is
copied or run. When it cannot answer, the program prints one line on standard
error that says what is missing and how to supply it, prints no report, and
exits `4`.

The report gives fast mode's test recall, change recall and selection rate with
their counts (`selection` under `--json`), how many questions the model answered
during the replay and how long that took (`model`), and each target fast mode
skipped, with its commit and the reason its score carries (`skipped` in each
commit, with `skipReason` always `predicted-safe`). The time the model took for
a commit is in that commit's fast-mode time and in `model` of the commit:

```text
fast mode
test recall      92%  11 of 12 failures
change recall    92%  11 of 12 failed changes
selection rate   63%  120 of 192 targets
the model answered 24 questions in 3m 05s, which is in fast mode's times
over the commits these times cover, fast mode's runs took 1m 42s less than normal mode's and asking the model took 1m 31s
```

When the model stops answering during the replay, the program stops using it.
The baseline and normal mode still run for every commit. The report is printed
in full with no fast-mode numbers, not even for the commits fast mode finished,
and it says fast mode was not measured and why. With `--json` the reason is the
report's `fastNotMeasured` field. The same line goes to standard error, and the
program exits `4`, also when the report lists a mismatch.

## Output

The report goes to standard output. While a replay runs, standard error gets one line as each mode of each commit starts:

```
smithers-ci: 2/5 3f2a1c9 baseline
smithers-ci: 2/5 3f2a1c9 normal
```

A replay runs commits. When the working tree has changes that are not
committed, standard error says first that they are not replayed. When this
machine cannot record what a step reads, standard error says so once, with the
reason.

`--out` is read from the directory you run the command in. When the file is
inside the repository, it is the one file the command writes there, and the
report's last line names it; otherwise that line says the run wrote nothing to
the repository. The last line also says what the replay ran: targets generated
from the newest commit, or the repository's
[own targets](../concepts/own-targets.md).

`smithers-ci inventory` prints, under the first line, each file it could not
read and each thing that belongs to no job, as `unsupported <feature>: <detail>`.
A workflow that does not parse is listed there and nowhere else.

## Exit codes

| Code | Name          | Meaning                                                                                                                                                                                                                       |
| ---- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`  | `ok`          | The command finished.                                                                                                                                                                                                         |
| `1`  | `mismatch`    | A replayed target's verdict in a mode differs from its baseline verdict, or `apply --check` found a file `apply` would change. A flaky target, which passed on a rerun, agrees with a pass and does not make the exit code 1. |
| `2`  | `usage`       | The command line was wrong: an unknown command or flag, a bad value, or a replay as root without --allow-root.                                                                                                                |
| `3`  | `unsupported` | The repository cannot be replayed: it is not a Git repository with a commit, it uses something Smithers CI cannot run, or its CI does not pass on this machine.                                                               |
| `4`  | `failed`      | A step of the command could not finish.                                                                                                                                                                                       |

Exit `3` also means the repository's CI does not pass on this machine: no job
passed the first run or the run after it, or, with `--no-trial`, no
step passed in the baseline of any replayed commit. The program then prints no
report and no speedup. Standard error gives the first failure: the step, its
command, its exit code and the line of its output that says what failed. That
line is the replay's own when it stopped the step, as it stops a push, else the
last one that reports an error, never a progress line, a line of counts, a
line of a stack trace below its error, or a line a package manager writes
around a script, such as npm's `> xo && ava` or pnpm's `[ELIFECYCLE] Test
failed.`; when no line reports one, it is the last line the step printed. A
step that printed nothing is reported with `it printed nothing`. When only some jobs
fail, the program exits `0`, the report lists them, and the speedup covers the
others. When only some commits fail, the program exits `0`, the report names each
failed step, and the speedup covers the commits where the CI passed.

A mismatch is defined in [How it works](../concepts/how-it-works.md#3-replay).
A report where normal mode's result differs from the baseline's has no speedup:
it leads with the number of mismatches and what to do, and `speedup` is 0 over 0
commits under `--json`. A mismatch of the run with the files `apply` writes
says why (`cause` under `--json`) and leaves the speedup as measured.
A target that failed and then passed on a rerun is `flaky`. The report counts
flaky verdicts apart from mismatches, and they never make the exit code `1`.

Ctrl-C (`SIGINT`) and `SIGTERM` stop the program: the step it is running is
stopped, its temporary copies are removed, and it exits `130` or `143`, as a
shell reports a program ended by that signal. A second signal ends it at once.

The program always ends with a line and one of the codes on this page. When
its own work stops before it has a result, because it waits for an answer that
never comes or meets an error of its own, it stops the step it is running,
removes its temporary copies, says on standard error where it was, and exits
`4`:

```text
smithers-ci: replay: stopped without an answer while running normal mode at 3f2a1c9
```

## Environment

The program reads these environment variables and no others. It never prints a
value. All but `PATH` and `SMITHERS_CACHE_TOKEN` choose fast mode's model or how
it reaches the model.

| Variable                          | What it is                                                                                                                                |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `PATH`                            | Where the program finds Node.js to run Smithers build, and `claude` for fast mode.                                                        |
| `HOME`                            | Where fast mode finds this machine's Claude Code and Codex logins.                                                                        |
| `USER`                            | The user whose Claude Code login fast mode uses. On macOS Claude Code keeps its login in that user's keychain.                            |
| `SMITHERS_CACHE_TOKEN`            | The token sent to the shared cache that `--cache` names.                                                                                  |
| `AI_GATEWAY_API_KEY`              | The key for the model that predicts which tests a change cannot break. Without it, fast mode uses the model this machine is signed in to. |
| `AI_GATEWAY_API_KEY_FILE`         | A file that holds that key, read when `AI_GATEWAY_API_KEY` is empty.                                                                      |
| `ANTHROPIC_API_KEY`               | When set, fast mode does not use this machine's Claude Code login. Unset it to use that login.                                            |
| `ANTHROPIC_API_KEY_FILE`          | A file that holds that key, read when `ANTHROPIC_API_KEY` is empty.                                                                       |
| `CLAUDE_CONFIG_DIR`               | Where Claude Code keeps its login, when that is not its default directory.                                                                |
| `CODEX_HOME`                      | Where Codex keeps its login, when that is not `~/.codex`.                                                                                 |
| `SMITHERS_OPENAI_AUTH`            | `chatgpt` lets fast mode use this machine's Codex login.                                                                                  |
| `OPENROUTER_API_KEY`              | A key for OpenRouter, which fast mode uses when no subscription can answer.                                                               |
| `OPENROUTER_API_KEY_FILE`         | A file that holds that key, read when `OPENROUTER_API_KEY` is empty.                                                                      |
| `SMITHERS_ACCOUNT_POOL_URL`       | The address of a Smithers account pool, which fast mode can use.                                                                          |
| `SMITHERS_ACCOUNT_POOL_KEY`       | The key for that account pool.                                                                                                            |
| `SMITHERS_ACCOUNT_POOL_PROVIDERS` | The providers that account pool serves, separated by commas.                                                                              |
| `SMITHERS_EVALUATOR_BASE_URL`     | Another address for the model, in place of the AI Gateway.                                                                                |
| `SMITHERS_MODEL_PROXY_URL`        | A proxy that carries fast mode's requests to its model.                                                                                   |
| `SMITHERS_MODEL_PROXY_PROVIDERS`  | The providers that proxy carries, separated by commas.                                                                                    |
| `HTTP_PROXY`                      | The proxy for fast mode's HTTP requests; `http_proxy` also works.                                                                         |
| `HTTPS_PROXY`                     | The proxy for fast mode's HTTPS requests; `https_proxy` also works.                                                                       |
| `NO_PROXY`                        | The hosts fast mode reaches without a proxy; `no_proxy` also works.                                                                       |

To sign this machine in instead of setting a key, run `claude auth login` with
`ANTHROPIC_API_KEY` unset, or `codex login` with `SMITHERS_OPENAI_AUTH=chatgpt`.
With neither a key nor a sign-in, `--mode fast` and `--mode both` exit `4` before
they copy or run anything.
