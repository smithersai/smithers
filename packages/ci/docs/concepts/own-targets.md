---
title: "A repository that already builds with Smithers build"
description: "What smithers-ci does on a repository with its own Smithers workspace: it converts nothing and replays the repository's own targets, cold against cached."
---

A repository with its own Smithers workspace has nothing to convert: its CI is
already its targets. On such a repository `smithers-ci` measures what the cache
is worth. It replays the last commits twice, once with no cache and once with a
cache kept between commits, and reports the difference.

```sh
bunx smithers-ci --commits 3
bunx smithers-ci replay --commits 3 --json
```

## How it is recognised

The newest commit holds `.smithers/WORKSPACE.ts` or a root `WORKSPACE.ts`, the
two places Smithers build looks, and `smithers-ci` did not generate it. A file
`smithers-ci apply` wrote starts with `// Generated by smithers-ci.` and does
not count.

`smithers-ci inventory` shows the fact as an unsupported entry with the feature
`smithers-build` and the workspace file.

## Nothing is generated or written over

- `smithers-ci apply` exits 3 with one line that names the workspace file, and
  writes nothing.
- The replay generates no workspace, no `PACKAGE.ts` and no workflow, in the
  repository or in its copies.
- On any repository, a generated `WORKSPACE` or `PACKAGE` file is never written
  over a file `smithers-ci` did not write. `apply` and the replay exit 3 and
  name the file.

## Which targets are replayed

The patterns the repository's CI gives Smithers build: every argument that
starts with `//` after `smthrs ci`, `smthrs test`, `smthrs lint` or
`smthrs build`, in a step of a job that a push, a pull request or a merge group
triggers. They run as one `smthrs ci` over all of them. `--shard`, `--known-red`
and the other flags of the CI's command are left out: shards of one run are one
run here.

When the CI names no pattern, for example because a script wraps `smthrs`,
every target is replayed: `//...`.

The report holds the patterns in `targets`, and shows them above the speedup.
It lists under "not replayed" each CI job with no step that runs a target: its
commands are not run.

`--targets` names other patterns, separated by commas:

```sh
bunx smithers-ci --commits 3 --targets //packages/ci/...
```

The report then lists each CI job with a pattern that the named ones do not
cover. On a repository with no workspace of its own, `--targets` is refused
with exit 3.

## Which `smthrs` runs them

The repository's own, at the version it pins. Smithers build refuses a program
from outside the checkout, and another version may not read the repository's
target files. So each checkout is installed first, in the directory of the
workspace file and then at the root, with the package manager the lockfile
there names:

| Lockfile                | Install command                                   |
| ----------------------- | ------------------------------------------------- |
| `pnpm-lock.yaml`        | `pnpm install --frozen-lockfile --prefer-offline` |
| `bun.lock`, `bun.lockb` | `bun install --frozen-lockfile`                   |
| `package-lock.json`     | `npm ci --no-audit --no-fund`                     |

The program is then `node_modules/.bin/smthrs` in the first of those
directories that has it.

## How one commit is run

Commits run oldest first. Each mode has its own copy of the repository; the
repository itself is never touched.

|                      | Baseline                            | Normal mode                         |
| -------------------- | ----------------------------------- | ----------------------------------- |
| Untracked files kept | none                                | the cache directory, `.flows`       |
| Dependencies         | installed again                     | installed again                     |
| Command              | `smthrs ci <patterns> --no-cache`   | `smthrs ci <patterns>`              |
| Shared cache         | not read                            | read when `--cache` names one       |
| A target's verdict   | from the run record `smthrs` writes | from the run record `smthrs` writes |

Both copies are cleaned of every other untracked and ignored file before each
commit. A build output left in the tree can change a target's key, so a copy
that was not cleaned would miss its own cache.

Fast mode runs in a third copy, as on any repository: the targets normal mode
ran, less the ones the scorer judges safe to skip.

## What is timed

A mode's wall time for a commit covers its checkout, its install and its one
`smthrs ci` run. The install is counted, and counted the same way in both
modes, because a CI machine pays for it either way. The speedup is therefore
lower than the ratio of the two `smthrs ci` runs alone; `workMs` in the report
is the sum of the targets' own time in each mode, with no install in it.

A failed target is run again to tell a failure from a flake. Those reruns are
not timed.

## How verdicts compare

Each target's verdict in normal mode is compared with its verdict in the
baseline, by label. A cache hit is a pass. A target skipped because a target it
depends on failed is skipped in both, so it is no mismatch. A mismatch means a
cached result disagrees with a fresh one: a target that reads something its key
does not cover, or a flaky target. A target that fails once and passes when run
again is `flaky`, which is not `pass`: on a busy machine a test that times out
shows up this way.

## What it prints while it runs

Standard error gets one line as each mode of each commit starts and one when
it ends, with its counts and its time, then a line for each of the first five
targets that failed, with the first line of the reason `smthrs` gave, and one
for each target that failed and then passed when run again:

```text
smithers-ci: 2/3 3f2a1c9 normal
smithers-ci: 2/3 3f2a1c9 normal: 1 ran, 6 from the cache, 0 failed, 0 skipped in 41 s
```

## A commit that cannot be installed

It is reported, never dropped: one failed result, labelled `(install)`, in
every mode, and the replay goes on to the next commit. The line on standard
error names the install command, its directory and its exit code. The command's
output is not shown, because it may hold a registry credential; run the command
in a checkout of that commit to read it.

## A build that does not run on this machine

When no target passes in the baseline of any replayed commit, there is nothing
to measure: `smithers-ci` exits 3 with the first failure of the newest commit.
That is what a missing tool looks like, for example a workspace that names
`go` as a host program on a machine without it, and what an install that never
works looks like. A repository whose install brings no
`node_modules/.bin/smthrs` gets this exit with a line that says it must depend
on `@smthrs/cli`.

When only some targets fail, they fail in the baseline and in normal mode
alike. The report shows both runs as failed, and standard error names the
targets and their reasons.

`smithers-ci` installs what the lockfiles name and nothing else. A repository
whose CI prepares more before it runs its targets, such as other installs a
script makes, has the targets that need them fail here.

When `smthrs ci` starts and writes no run record, `smithers-ci` exits 4 with
what `smthrs` printed.

## Reproduce a number by hand

At one commit, in a clean checkout:

```sh
git clean -ffdx
pnpm install --frozen-lockfile --prefer-offline
node_modules/.bin/smthrs ci '//packages/ci/...' --cache-dir .flows --no-cache --results-file cold.json --ui plain
```

That is the baseline. Normal mode is the same without `--no-cache`, in a
checkout that kept `.flows` from the commit before.
