Method and limits

The immutable task corpus has 50 tasks: ten fixed seeds in each of filtering, grouping, deduplication, joins and tag normalization. Both arms receive identical task instructions and records, the same model, credential cohort, reasoning effort and six-turn ceiling. The cell arm emits JavaScript in a persistent production QuickJS realm; the tool arm uses native function calls. Both read through the same recorded records action and submit an object. The evaluator compares canonical JSON with an independently prepared answer. Expected answers never enter model requests.

Tasks run sequentially; arm order alternates by task to balance drift. Each call has one attempt, without benchmark retries. Fixture seeds fix inputs; the subscription endpoint exposes no sampling seed. There is one stochastic sample per task and arm. These small synthetic data tasks do not establish coding-agent performance, production latency, or general model superiority. Prompt formats and executable computation differ by design. Warm provider cache and shared-host load are uncontrolled. Time includes model calls and realm/tool execution but excludes runtime startup.

Access, provider and harness failures remain attempted runs; they count as end-to-end failures but are excluded from the task-quality paired difference. Exclusion can bias that conditional difference. The paired Hoeffding bound is distribution-free for independent task-pair observations, a conservative assumption that shared provider state may violate. Wilson intervals describe each arm's end-to-end success under a binomial working model. The fixed convenience corpus is not a random sample of real workloads.

Token counts are provider observations; absent counts are unknown. USD values, where available, are estimates using the SDK price-table snapshot retained in the manifest, not subscription invoices. Any unpriced turn makes the total unknown. Subscription per-call billing is not exposed. Provider failures may incur unreported usage or charges. Task hashes, requested model (an alias, not a verified immutable provider snapshot), cohort and source identities are retained below. Normalized SDK events and requests are raw receipts at the SDK boundary; HTTP headers and credential values are never captured.
