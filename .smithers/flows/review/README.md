# Review

`/review` is a registered `Flow.make("review", ...)` flow. It reads a working-copy change (including jj), a commit, or a revision range, reviews files in bounded batches, independently verifies findings, and produces a narrated walkthrough. `review/change` remains available for the focused child prompt.

Where `repo` holds `.jj`, `commit`, `from` and `to` are jj revsets, read without snapshotting the working copy: `commit` must name one commit, and a range diffs `to` against `fork_point(from | to)`. A jj workspace beside its repository has no `.git`, so this is the only way to review its commits. Otherwise they are Git revisions, and a range diffs `to` against the merge-base. Either way the revisions are pinned to commit ids once, and the repository's `.opencodereview/rule.json` is read from the commit's parent or the fork point, never from the change under review.

Run it through the normal app flow catalog or `smthrs flow start review --data '{"repo":"."}'`. The host supplies the engine, identity, permissions, filesystem, process launcher, model aliases, policy, and budget. The module exports implementations only; it does not start a service, create an engine, resolve credentials, or choose a budget. Review and verification use the host's `coding/review` seat; narration uses `coding/implement`. The coding host maps both roles; on the plain `smthrs` host, pin them with `SMITHERS_SEATS='{"coding/review":"sol","coding/implement":"opus"}'`. `smthrs runs output <run> result --format json` answers the completed run's typed result. The land gate runs this flow with `node .smithers/flows/land/review.mjs --flow --rev <revset>`.

A host without a checkout registers the rounds from `src/workflow/reviewFlow.ts`, `src/workflow/reviewActions.ts`, `src/review/preparedReviewOf.ts` and `src/github/comparisonSnapshot.ts`, which import no platform module (`tests/workflow/hostFreeRounds.test.ts` fails if one does), and supplies its own `PrepareReview` and `RenderWalkthrough`. The checkout-reading and file-writing implementations of those two live in `src/workflow/reviewHostActions.ts`.

`comparisonSnapshot` turns GitHub's comparison of two commits (`GET /repos/{owner}/{repo}/compare/{base}...{head}`, its `files` and whether it was cut at GitHub's file limit) into the same snapshot `loadReviewSnapshot` reads from git: a `range` review of `base..head` whose records match git's diff of the same change. A file GitHub sends without a patch is binary when it counts no lines, and is skipped as `patch_withheld` when it counts lines GitHub would not show. The repository's `.opencodereview/rule.json` is not read, because a comparison carries no file contents.

The typed result retains findings, coverage gaps, warnings, story and artifact receipts, and a `verdict` read from the post-verification review:

| `verdict`    | When                                                                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pass`       | Status `success`, every finding verified, and none at `major` or above.                                                                                         |
| `fail`       | Status `success`, every finding verified, and a `critical` or `major` finding stands.                                                                           |
| `incomplete` | Any other status (`skipped`, `completed_with_warnings`, `completed_with_errors`, `failed`), or findings left unverified (`verifier_error`, `verifier_skipped`). |

`major` is the blocking threshold because the file prompt defines `critical` as "the merge must stop" and `major` as "a real bug users will hit"; `minor` and `info` are advice. An outage, a failed file review or a verifier that could not rule therefore never reads as a pass, nor as a fault in the code. With `verify: false` nothing is verified, and findings count as the reviewer wrote them. Narration writes the story only, so a narrator failure marks the review `completed_with_warnings` without changing the verdict. A result stored before `verdict` existed decodes as `incomplete`. Its `ui: { kind: "html", title, html }` field uses the common authored result renderer: an isolated iframe in the embedded run card. Any other flow may return the same shape. Scripts cannot access the app, navigate the parent, submit forms, or fetch external resources. The generated walkthrough also remains a self-contained HTML artifact.

All repository reads and commands go through the caller's filesystem and process services. Cancellation interrupts model calls and host child processes. Timeouts preserve partial findings and visibly mark failed or unverified work. The host's exhausted budget prevents model calls; no private review billing or proxy exists.

The old standalone app, CLI, HTTP service, sessions, publishing, billing proxy and quiz are removed. Walkthrough RPC responses and the app expose sections only; historical database quiz data remains readable without affecting sections, and new writes store an empty legacy column.
