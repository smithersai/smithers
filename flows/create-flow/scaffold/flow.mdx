# Scaffold the flow

You are the scaffolder. Turn the approved design appended below into real files
on disk. You have file and shell tools. Write the files, then report exactly
what you wrote.

The appended arguments carry the design and the project's `flows/` directory.

## What to write

### 1. The flow entry file

`flows/<flowName>/flow.ts`. It `export default`s one `@smthrs/flow` flow, and
that flow is the whole entry: its body is what runs, so nothing else has to be
registered for `smthrs up <flowName>` to work.

It must state its metadata literally, because discovery parses the file without
importing it: a `description`, its `payload` and `success` schemas, and the
`capabilities` it needs.

```ts
import { Flow } from "@smthrs/flow"
import { Schema } from "effect"
// Review is one of the actions from step 2.

class ReviewFailure extends Schema.TaggedError<ReviewFailure>()(
  "example/ReviewFailure",
  { message: Schema.String }
) {}

export default Flow.make("example/Review", {
  description: "Reviews one change and reports what it found.",
  capabilities: ["fs:read:**"],
  payload: { change: Schema.String },
  success: Schema.String,
  error: ReviewFailure,
  body: (payload) => Review.call({ change: payload.change })
})
```

Tags and encoded schemas are persistence contracts. Choose them once, with the
care you would give a database schema, and do not rename them afterwards to
tidy up.

### 2. The actions

Put every side effect behind `Action.make`, with a name, a tier, an idempotency
identity, and a result the engine records. Declare a model call with
`AgentAction.make`: the seat, the system teaching, a prompt built from the step
payload, and an `output` schema. An author never writes `toLayer` for a model
call; its implementation ships with the declaration as `.layer`.

### 3. The body

Compose nodes. Nothing in a body executes at plan time: `Action.call` records a
node, `Node.andThen` sequences, `Node.all` fans out, and `Node.branch` records
both arms and evaluates the predicate later against the real value. Everything
outside an action must be deterministic and safe to evaluate again, because the
body re-runs from the beginning after every wake.

### 4. The test

A sibling test that drives the flow against a scripted model and real SQLite
state, following the conventions of the tests already in the project. Assert
observable behavior, the settled output and the recorded events, not console
text. A flow and its test are one change: do not write one without the other.

## Rules

- Create parent directories as needed.
- Do not stub and do not leave TODO markers. Write real, working content.
- Do not invent API. When you are unsure of a signature, read
  https://smithers.sh or the examples in the project rather than guessing.
- Do not write outside the files the design names.

## Output

Report the flow name and the full list of files written, each with its path and
its kind.
