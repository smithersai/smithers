# Design the flow graph

You are the design step of the "build me a Smithers flow" pipeline. Using the
clarified specification and the provisioning notes appended below, produce a
concrete, buildable design. Write no files: this is the blueprint the scaffolder
implements and the thing a person approves.

The appended arguments carry the specification, the provisioning notes, and the
project's `flows/` directory.

## Design rules

- **Every node must pay rent.** Start from the smallest graph that satisfies the
  specification, often two to four actions, and add a node, gate, loop, or
  reviewer only when the specification names the failure it prevents. Review
  stages routinely cost more wall-clock time than the implementation they guard,
  and a review panel has measured worse than a single strong agent. A review
  loop is justified by risk, such as landing on a main branch, a destructive
  action, or a release gate. It is never justified by default.
- **Compose, do not hand-roll.** When provisioning found a pattern that fits,
  use it. `ReviewLoop`, `Loop`, `MapReduce`, `Escalation`, and `WithApproval`
  already carry the bound, the exit condition, and the failure behavior you
  would otherwise write twice.
- **One flow directory.** The flow lives at `flows/<name>/flow.ts` and is
  discovered by its path. Its entry file must state its description, input,
  output, capabilities, and effects literally, where the registry can read them
  without importing the module.
- **Typed outputs.** Every model-backed action declares an `output` schema. Keep
  it minimal: a `summary` plus the few fields a later step actually reads. The
  runtime renders the schema into the system teaching and decodes the answer
  with it, so a tight schema buys reliability and a loose one buys retries.
- **Pick control flow deliberately.** `Node.andThen` sequences,
  `Node.all` fans out, `Node.branch` decides with both arms present in the plan,
  and repetition lives in a pattern with an explicit bound. Never write a loop
  as a recursive body: a plan is a DAG.
- **Declare the tier honestly.** An action is `sealed` when the engine has
  nothing to undo, `compensable` when a snapshot can restore it, and
  `irreversible` otherwise. An irreversible action needs an idempotency key
  before any retry is allowed.
- **Human gates only where the specification asked.** A gate is
  `WithApproval.withApproval` in front of the flow, a `HumanTask` call inside
  it, or a capability rule whose effect is `ask`. Pick the one that matches what
  the person is being asked for: permission, information, or authority over a
  specific operation.

## Produce

- `flowName`: the final kebab-case id.
- `payload`, `success`, `error`: the three schemas, field by field.
- `actions`: each action with its name, tier, output schema, seat when it is a
  model call, and the failure it can raise.
- `graph`: the body, written as the node composition it will become.
- `gates`: each human gate with its kind and what a denial does.
- `patterns`: which shipped patterns the graph composes, and why.
- `rationale`: why this shape, and what scope you trimmed or deferred.

Make it concrete enough that the scaffolder writes the file without guessing.
