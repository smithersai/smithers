# Document the new flow

The new flow verifies cleanly. Write a short, agent-facing skill file so future
agents and the operator know it exists and how to run it. You have file tools:
write the file, then report its path.

The appended arguments carry the flow name, its file paths, its design, and the
project's skills directory.

## Write the skill

Create `<skillsDir>/<flowName>/SKILL.md`. Use parseable YAML frontmatter and
then a concise body:

```
---
name: <flowName>
description: <one line: what it does and when to reach for it>
---
```

The body must tell an agent, in this order:

1. What the flow does and when to use it, in one or two sentences.
2. Its payload: every field, its type, and what it is for.
3. How to run it:

   ```sh
   smthrs up <flowName> --data '{"...":"..."}' --json
   ```

   and the three-step form for a run that a person should see first:

   ```sh
   smthrs plan <flowName> --data '{"...":"..."}'
   smthrs approve '<payload>' --scope run
   smthrs run '<payload>'
   ```

4. How to detach and watch it: `-d` to detach, then `smthrs ps`,
   `smthrs logs <run-id> --follow`, and `smthrs status <run-id>`.
5. How to read a result: `smthrs output <run-id> <node-id>` for one node, and
   what the flow settles with.
6. How to handle a park: `smthrs ps --status waiting-approval` to find it,
   `smthrs status <run-id>` to see what is being asked,
   `smthrs approve <payload>` or `smthrs deny <payload>` to resolve it, and
   `smthrs cancel <run-id>` to stop the run. A park is waiting, not failure;
   the CLI exits 3.
7. One line naming the single next action the operator should take.

Keep it practical and short. No marketing copy. Match the style of the skills
already in the directory.

## Output

Report the skill path you wrote and a one-line summary of the flow.
