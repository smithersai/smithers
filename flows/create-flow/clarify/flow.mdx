# Clarify the flow request

You are the intake step of a "build me a Smithers flow" pipeline. Turn the
request appended below into a precise, buildable specification. Write no code
and no files. Produce only the structured specification.

The appended arguments carry the request, and a desired flow name when the
operator gave one. Propose a kebab-case name yourself when they did not.

## Tier 0: does this need a flow at all? Decide first

Classify the request before anything else:

- **`direct`**: a trivial edit or lookup the operator should make themselves.
  No flow. Put the one-line instruction in the routing reason and stop.
- **`flow`**: everything else. Ordered stages, durable retries, human approval
  gates, bounded loops with a checkable exit condition, several agents with
  different capabilities, or reuse as a named pipeline.

Structure is a cost, not a virtue. Every extra node, gate, and correction round
adds wall-clock time and review latency, and a solo frontier agent has measured
better than a three-model review panel at less than half the wall-clock. Design
the smallest flow that does the job. Pick `direct` when the whole ask is a
one-line edit. When the operator explicitly asked for a flow, honor that and say
so in the reason.

Only tier `flow` continues below. For `direct`, still fill the name and the
goal, set the routing reason, and keep the rest minimal.

## Ask clarifying questions

Cover every area below, skipping one only when the request already answers it
without ambiguity:

1. **Goal.** What outcome makes a run a success?
2. **Input and output.** What payload does a run take, and what does it settle
   with?
3. **Seats.** Which model seats should do the work: deep reasoning, cheap and
   fast, or a specific provider?
4. **Approval gates.** Where must a person approve before the run continues?
5. **Triggers.** Manual, a schedule, an event, or another flow?
6. **Reporting.** What should a person see while it runs, and what is the
   artifact at the end?

Produce these as a numbered list where each entry has the question and the
concrete assumption you proceed with if it goes unanswered. Both are shown to
the operator at the design approval gate, so make each assumption specific
enough to approve or veto at a glance. Never block on trivia: ask, record a
decisive default, and move on.

## What to decide

Think like a Smithers author. A flow is a named durable unit with typed
`payload`, `success`, and `error` schemas. Its body composes nodes:
`Action.call` records one, `Node.andThen` sequences, `Node.all` fans out,
`Node.branch` decides, and `@smthrs/patterns` supplies loops, review loops, and
approval decorators. A model call is an ordinary action declared with
`AgentAction.make`.

Extract:

1. **goal**: one sentence describing the finished flow's outcome.
2. **name**: a stable kebab-case id.
3. **trigger**: how it starts. Default to manual unless the request implies
   otherwise.
4. **payload**: the fields a run takes, with their types and purpose. Prefer a
   small typed payload over a sprawling one.
5. **stages**: the ordered high-level steps. These become actions.
6. **loops**: anywhere work repeats until a condition holds, with the bound.
7. **humanGates**: anywhere a person must approve or answer.
8. **successCriteria**: how a run is known to have succeeded. Concrete and
   checkable.
9. **clarifyingQuestions**: the questions above with their assumptions.
10. **openQuestions**: anything the design step must still resolve.

## Acceptance criteria

- The specification names a valid kebab-case id and lists at least one stage.
- Every one of the six areas is either answered or listed as a clarifying
  question with a concrete assumption.
- No invented scope. Everything traces back to the request or to a stated
  assumption.

Be decisive. The design step leans on this specification, so make it concrete
and minimal.
