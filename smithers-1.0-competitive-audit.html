Smithers 1.0 Competitive Audit

What Smithers 1.0 supports, what its closest competitors support, where they overlap, and a ranked list of what to build or fix. Four market-research agents ranked the field; thirty agents each compared one feature's implementation against competitors' docs; three built feature checklists and one assessed the gaps.

Feature IDs: G1–G30Competitors profiled: 41Suggestions: see Section 6

Summary

Where Smithers 1.0 is ahead. Nobody else builds a content-addressed plan before execution with per-step read, write and tier declarations that are checked at run time and an approval bound to the plan digest. Nobody else keys replay by declared inputs and schemas so resume survives code changes, or journals every code-action call from a sandboxed cell, or refuses a rewind across an irreversible effect, or ships agents as cached build targets. The engine's fencing, quota parking, snapshot compensation, triage safety and eval regression semantics are each more careful than any competitor's.

Where it is behind. Three areas matter most. Safety: an approved shell command runs on the host with full authority, the TUI accepts every permission by default, and three authorization gaps let a local agent approve its own gates. Promised but undelivered: memory policy fields that do nothing, a migrate table that says seven shipped patterns do not exist, documented cache-token commands that are absent, a dispatcher that cannot register rules, an LSP client that never syncs files, exporters nothing turns on. Money and models: no dollar accounting anywhere, no fallback seats for flows, and a ChatGPT-subscription route that spoofs Codex's user agent.

Closest competitors. Mastra on the framework side, Nx on the build-graph side, Archon and Claude Managed Agents on the coding-harness side, Ona and Devin on the hosted side, and Effect Workflow underneath, which Smithers' engine is a fork of. Cloudflare Code Mode is the nearest prior art to cells. Full rankings are in Section 2.

What to do first. Items 1 to 5 in Section 6 are security defaults and a terms-of-service liability. Items 6 to 8 are cost and model routing. Items 9 to 32 are the remaining MUSTs: durability and plan gaps, coding-flow review, control-plane basics, observability, evals, memory, and the hosted product's dead ends. Everything is tagged with the feature ID and effort.

What Smithers 1.0 supports

Smithers 1.0 is "the codebase maintainer agent": flows declared beside the code, a durable Effect-based engine, a capability kernel, a harness where the model writes JavaScript cells, a TUI coding agent, a Bazel-like build graph, and a hosted app at smithers.sh. MIT-licensed libraries and CLI; hosted plans sold by sandbox capacity. Each feature carries an ID used throughout the report. A caution mark flags something the code or docs promise but do not fully deliver; Section 5 has the evidence.

Where Smithers stands alone

  • No competitor combines a content-addressed plan built before execution, per-step read/write/tier declarations checked at run time, and an approval bound to the plan digest.
  • No competitor keys replay by declared inputs and schemas so that resume survives code changes. Everyone else replays by position or step name.
  • No competitor journals every code-action call from a sandboxed cell and replays it; smolagents, Code Mode, Anthropic programmatic tool calling and Monty keep no journal.
  • No competitor ships agents as cached build-graph targets, restores the workspace automatically before a compensable retry, or refuses a rewind across an irreversible effect.

G1 Flow authoring AHEAD ON RIGOUR, BEHIND ON ERGONOMICS

Today. Two different Flow.make signatures exist: flow uses (name, {payload, success, error, body}) and core uses ({name, input, output, body}). Bodies are pure plan builders; step results are Planned placeholders and every decision goes through Node.branch. Node.all is the only join, takes a record, and has a plan-time width. Runtime-sized loops and fan-out go through boundaries (.to rounds or .child executions) with explicit build-time refusals, which is ahead of every competitor. Markdown flows are single-prompt with input fixed to a string and no templating. A two-step typed flow needs about 25 lines plus 20 to 40 lines of layer composition to run.

Competitors. Mastra chained builder with foreach and dountil; LangGraph Send and Command; Vercel plain async with Promise.race against durable sleeps; Effect Workflow's Workflow.make, which Smithers' signature mirrors; ADK 2.0 graph edges with JoinNode and DynamicNode; Claude Code workflows where a two-step flow is two lines.

  • Race, any and quorum joins with cancellation of losers recorded in the journal. MUST, M.
  • Unify Flow.make into one signature. MUST, S.
  • Node.forEach over a planned array lowering to a child or round. SHOULD, M.
  • Typed markdown flows: honour input and output frontmatter and strict templating. SHOULD, M.
  • Flow.runLocal that composes engine, crypto, registry and seats. SHOULD, S.
  • Node.loop sugar over rounds. NICE.
G2 Plan-time graphs AHEAD

Today. Graph.build evaluates bodies against a symbolic placeholder and refuses computed values; Plan.compile keys each step by body, inputs, layers, capabilities, effects and placement so renames do not re-key. Steps declare reads, writes, mode, onConflict and tier; a step can narrow but never widen its parent's envelope; WorkspaceSandbox checks the declared writes at run time in hard or expected mode. Plan approval binds to the keyed-graph digest. The app draws the graph with source links and a critical-path ETA. Planning runs author code with ambient authority; no Mermaid export; no token or cost estimate; multi-round runs have no whole-run view.

Competitors. Bazel aquery and Nx sandboxing audit inputs; LangGraph and Pydantic render Mermaid; MS Agent Framework exports SVG; Cloudflare Dynamic Workflows and Temporal have no plan at all; Dagster's asset graph is the nearest data-dependency model.

  • Isolated planning for untrusted flows, or the data-only declaration format the docs recommend. MUST, M to L.
  • Mermaid, DOT and text export of a PlanCard. SHOULD, S.
  • Token and USD estimate per node from past usage, plus a budget pre-check. SHOULD, M.
  • Declarative policy over plan effects evaluated in ApprovalAuthority. SHOULD, M.
  • Whole-round lineage view; affected-style auto-approval when only cached nodes changed. NICE.

Verdict. No product combines content-addressed keys, per-step effect declarations checked at run time, and digest-bound approval.

G3 Durable engine AHEAD ON FENCING, BEHIND ON VERSIONING

Today. Sealed actions with an idempotencyKey get content keys; everything else gets ordinal keys; concurrent keyless dispatch and keyless irreversible retries are refused; corrupt evidence is quarantined. Ownership is fenced on host, pid and nonce with a 1 s heartbeat and a 30 s stale window; the driver sweep re-drives released and stale runs automatically; DisasterRecovery.fence handles backup restore. SQLite only, with opt-in compaction and retention. Journal sync is read-only replication, so multiple hosts cannot execute. Resume across code changes means unchanged keys replay and changed keys re-run; a different implementationVersion needs a new execution id.

Competitors. Temporal worker versioning and patched(); DBOS application versions, patch, fork and rewind; Restate immutable deployments; Vercel deployment pinning with opt-in latest; OpenWorkflow leases; Effect Cluster sharding.

  • Record the flow and engine fingerprint per run and check it on resume with an explicit override. MUST, M.
  • Flow.patched marker for deterministic old-versus-new branches. SHOULD, M.
  • Drain view: unfinished runs per fingerprint. SHOULD, S.
  • Document and test fork as the upgrade path. SHOULD, S.
  • Journal size warnings and scheduled retention under serve. NICE, S.
  • Shared execution backend for fleets, post-1.0. NICE, L.
G4 Time travel AHEAD ON REWIND, BEHIND ON FORK

Today. Replay reads the journal through a projection at no model cost.
