Status: unreleased. These notes describe the current 1.0 rewrite. They do not certify a published artifact or announce a completed release rehearsal.

Smithers 1.0 replaces the 0.x JSX workflow engine with typed flows and actions over Effect, a durable SQLite engine, and a target graph for builds and tests. A run records its work so a later process can continue from persisted state.

## Install

The release is not on npm; install from the source checkout ([Installation](https://github.com/smithersai/smithers/blob/main/packages/smithers/docs/installation.md#install-the-cli)). The CLI requires Node.js 26.4.0 or later, and Effect and its platform packages are pinned to exactly `4.1.1`. See the [support matrix](/docs/reference/support-matrix/).

## Authoring and execution

- `Flow.make`, `Action.make`, `Interpreter.layer`, and Effect replace JSX workflow components. Action declarations and their implementations are separate.
- Markdown agent flows run through `smthrs flow start` with a configured model seat. Hosts register module flows and their action implementations with the durable runtime and provide `Executable.Catalog`. `AgentSession` executes a native module matching its approved descriptor as a durable child, retaining its actions, waits, and replay. Without a catalog or a registered delegate, execution remains `pending`. See [module flows](/docs/guides/module-flows/).
- `WORKSPACE.ts` and `PACKAGE.ts` declare the target graph. `smthrs test`, `build`, and `lint` select targets; declared inputs and execution identities control caching. [The first-target tutorial](/docs/tutorials/first-target/) exercises a cache hit and input invalidation.
- The agent runtime evaluates model-authored cells in QuickJS with declared flow tools and budgets. Typed output schemas validate values before downstream steps consume them.

## Durable state and control

Node.js and Bun support durable execution through `NodeRuntime` and `BunRuntime` with SQLite or PostgreSQL. The control plane uses `.flows/control.db`, the engine uses `.flows/engine.db`, and artifacts live under `.flows/objects/`. Services sharing a database must initialize their complete ordered migration set before opening later schema blocks. Internal pre-release schemas and 0.x run databases carry no compatibility promise.

| Feature | Current surface |
| --- | --- |
| Durable waits | Deferred values, timers, signals, and human tasks survive engine restarts. |
| Retry and ownership | Retry bounds are recorded with attempts. Claims, leases, and same-host process probes prevent a live peer's run from being stolen. |
| Run control | `runs cancel`, `runs steer`, `runs signal`, `runs resume`, `approvals approve`, and `approvals deny`, subject to the host's authorization policy. |
| Execution history | `smthrs runs inspect`, `replay`, and `verify`, plus the `@smthrs/time-travel` library. Replay reads history without dispatching actions. Forks may repeat external effects; eligible sealed results require an explicitly shared cache environment. |
| Compensable writes | A real snapshot boundary is required. Host snapshots do not provide generic rollback for external services. |
| Memory | Structured facts and FTS recall over SQLite; namespaces and memory policy determine visibility. |
| Backup | `@smthrs/engine-store/DisasterRecovery`; source checkout script `packages/smithers/flows/engine-store/scripts/flows-backup.mjs backup\|verify\|restore`. |

See the [support matrix](/docs/reference/support-matrix/) for runtime ranges, tested toolchain pins, platform boundaries, storage, and hosting requirements. `BunRuntime` uses the native Bun SQL driver; restart coverage exercises Node-to-Bun and Bun-to-Node recovery. Browsers run durable flows through `BrowserRuntime` over SQLite in OPFS in a dedicated worker, with one leader per origin elected by a Web Lock. All tabs closed pauses execution; reopening the same browser profile resumes unfinished runs. Browser storage may be cleared, and profiles and devices have separate stores. Cloudflare Workers use `CloudflareRuntime` over PostgreSQL; Deno and other edge runtimes are unsupported. Windows is best effort; macOS CI is advisory.

## Hosting and credentials

The control plane is unauthenticated on loopback by default. Configure authentication and TLS termination before exposing it to other machines. `ControlClient.credential` applies to HTTP; a browser WebSocket watch does not carry that credential. Gateway authorization is a host composition choice. See [serving beyond loopback](https://github.com/smithersai/smithers/blob/main/packages/smithers/gateway/docs/guides/serve-beyond-loopback.md) and the [support matrix](/docs/reference/support-matrix/#network-and-hosting).

Journal and logger redaction recognize credential fields and known token shapes. Arbitrary secrets can still enter executable state or raw child-process output; output schemas and host integrations must handle those values deliberately.

## Package inventory

The release roster contains 49 packages. `node scripts/pack-release.mjs --names` prints the authoritative set in publication order. [The manifest inventory](/docs/reference/support-matrix/#published-node-engine-ranges) records each package's Node requirement. `@smthrs/flows` is the curated aggregate, `@smthrs/cli` provides both `smthrs` and `smithers`, and `@smthrs/targets` provides target declarations.

Published export maps define the public API. `internal/` subpaths are excluded. The unscoped `smthrs` package is a migration notice, not the 1.0 authoring facade.

## Compatibility promise

> Smithers 1.0.0-rc.0 is a source migration, not a compatible upgrade. It provides no JSX workflow API, no `smthrs/jsx-runtime` or `smthrs/jsx-dev-runtime`, no React reconciler, no `<Workflow>`, `<Task>`, `<Sequence>`, `<Parallel>`, `<Loop>`, `<Ralph>`, `<Branch>`, `<Approval>`, `<Signal>`, `<Timer>`, `<Subflow>`, `<Worktree>`, or `<Saga>` components, no `createSmithers`, `runWorkflow`, `renderFrame`, or `SmithersCtx`, no `smthrs` facade, no 0.x CLI verbs beyond those listed in the 1.0 command table, no 0.x gateway protocol, and no ability to load, resume, or migrate 0.x run databases. No shim, adapter, or compatibility layer will be published. Flows are written against `@smthrs/flow` (`Flow`, `Action`, durable waits, `RetryPolicy`), `@smthrs/engine`, `@smthrs/control`, and Effect `4.1.1`, and run on Node.js 22.19.0 or later with local SQLite. Existing 0.x projects migrate their source with the `migrate-smithers-v1` workflow (`smithers migrate`), which rewrites workflows, imports, configuration, scripts, and docs and reports every construct it could not translate. Runtime behavior between 0.x and 1.0 is not equivalent and is not intended to be.

## Migrating source

Finish or archive 0.x runs with the old CLI, then use `smthrs migrate` to plan the source conversion. `--apply --seat <provider:model>` executes it after the migration gates pass. Read the generated report and run the project's own checks. Verify migrated module flows through their application host; discovery alone does not prove execution. The [migration guide](/docs/migration/1.0/) lists removed commands, unsafe constructs, and run-state refusals.

## Release validation

Before publishing, run the required checks and the tarball consumer rehearsal on the exact candidate commit. Record the commit, runtimes, commands, and results with the release evidence. Earlier review transcripts and internal development runs are historical evidence; they do not certify a later candidate.

Publication, tagging, and deployment remain explicit maintainer operations.
