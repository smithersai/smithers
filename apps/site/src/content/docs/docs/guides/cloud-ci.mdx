Smithers' backend dispatches repository workflows from matching events and executes CI on its sandbox plane. The proposed `S.Automation` API is still unimplemented; it is separate from the workflow service that runs today. Hosted availability depends on the repository connection and deployment's execution services.

## What runs checks today

The target graph runs wherever the CLI is installed; a workflow job can invoke it:

| Path | What it does | Where it is documented |
| --- | --- | --- |
| Smithers Cloud workflow | Loads repository workflow definitions for an event, queues CI, and runs jobs through the backend sandbox scheduler. Jobs can invoke `smthrs ci`. | [Cloud CI reference](/docs/reference/cloud-ci/) |
| `smthrs ci <pattern>` | Runs build, test, lint, and docs targets as one graph on the machine you run it on, with normal cache reuse. | [Build targets](/docs/guides/build-targets/) |
| `Smithers.GithubCiGen` | A target that generates the GitHub Actions workflow files from declared attrs. GitHub Actions then runs `smthrs ci` on push and pull request events. | [`@smthrs/targets`](/docs/reference/api/targets/) |
| `smthrs flow start` in a CI job | Launches a durable flow from GitHub Actions and gives the job an exit status when the run completes, fails, or parks. | [Run flows in CI](/docs/guides/ci/) |

This repository's [`.smithers/workflows/ci.tsx`](https://github.com/smithersai/smithers/blob/main/.smithers/workflows/ci.tsx) declares push-to-main and manual triggers. Its task groups invoke [`scripts/ci/cloud.sh`](https://github.com/smithersai/smithers/blob/main/scripts/ci/cloud.sh), including package, app, docs, and drift checks. A checked-in declaration alone does not prove a particular Cloud run succeeded.

For scheduled flows, use the app's [Dispatcher](/docs/app/dispatcher/) to prepare and approve a registration. To host the local scheduler yourself, use `smthrs serve` or `smthrs triggers serve`; see [Define triggers](/docs/guides/triggers/).

## Verify a Cloud run

Inspect the run's source revision, job results, logs, and final status. Connected GitHub repositories can receive a check named `smithers / <workflow name>` when the deployment supplies the GitHub App services. A queued run or accepted dispatch is not a passing check. Confirm the actual check name and completed result before making it required.

For Smithers' own factory, Cloud owns coding and CI/CD; GitHub retains synchronization and essential checks. See [the contributor workflow](https://github.com/smithersai/smithers/blob/main/CONTRIBUTING.md).

## Planned: event-driven Cloud CI

This section describes a declaration API that is not built. `@smthrs/targets` exports no `S.Automation` and `S.Package` accepts no `automations` entry. The type-level proof is [`apps/site/examples/cloud-triggers/contract.d.ts`](https://github.com/smithersai/smithers/blob/main/apps/site/examples/cloud-triggers/contract.d.ts); it does not implement trigger registration, matching, dispatch, or the `S.Automation` runtime.

The intended shape declares a suite and binds it to repository events in `PACKAGE.ts`:

```ts title="PACKAGE.ts (planned; does not compile against the released packages)"
import { Smithers as S } from "@smthrs/targets"
import { Trigger as T } from "@smthrs/triggers"
import { Package as src } from "./src/PACKAGE.js"

const checks = S.Suite({
  tests: [src.lint, src.typeCheck, src.test],
})

const ci = S.Automation({
  on: [T.push({ branches: ["main"] }), T.review({ base: ["main"] })],
  run: checks,
})

export const Package = S.Package({
  targets: { checks },
  automations: { ci },
})
```

The proposal would bind target or flow labels directly to typed selectors in `PACKAGE.ts`. Use the existing workflow service or registrar until that API is implemented; the example above does not compile against the current packages.
