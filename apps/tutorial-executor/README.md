# Anonymous tutorial execution

The public Worker authenticates to the tutorial coordinator. The coordinator owns the actual Smithers Flow/model loop and its SQLite journal. It imports `src/KubernetesExecutor.ts`, which creates one GKE Sandbox (`gvisor`) pod for each opaque tutorial session. No GitHub account, repository import, or personal workspace is needed.

Each executor receives only the pinned example source, a Node/Git toolchain and fixed host-owned regression tests. Its six HTTP operations are snapshot, files, apply, test, commit and diff. The model can edit only `src/hello.ts`, `src/hello.test.ts` and `README.md`. Tests invoke Node directly with the permission model, no filesystem-write or subprocess grants, and no process isolation (the enclosing gVisor pod already isolates the visitor). The test runner needs read access to its own credential-free container for file discovery. No repository-supplied package script executes. A zero exit code is accepted only when all three protected regression verdicts were recorded. Commits carry a hashed run key, making retries return the same actual commit and parent. No model/provider key, coordinator service token, Kubernetes token, shared directory or persistent volume is mounted in executor pods. Egress is denied. The workspace is limited to 128 MiB, tests to 20 seconds, output to 128 KiB, memory to 512 MiB and lifetime to one hour. A namespace quota caps concurrent pods at 20.

The coordinator is a separate single-replica Deployment in `smithers`, backed by a 1 GiB PVC and a Recreate strategy. Its Service lives beside the existing GCE ingress, which routes only `/__tutorial` to it. Executor pods live in `smithers-tutorial`; the coordinator service account can manage pods only in that namespace. The dedicated coordinator Secret contains the service token, a genuine existing Gemini provider credential and model selection `gemini-3-flash-preview`. Releases select the inherited `GEMINI_API_KEY`, then the existing dedicated credential, then the shared credential; placeholder values are rejected. The Worker receives only the service token and service URL. Existing Worker identity and Durable Object bindings are not changed by this deployment.

## Release

1. Run `python3 apps/tutorial-executor/infra/smoke.py` from the repository root. It builds the production executor and exercises real Node tests and Git commits in a restricted Docker container.
2. Build and test `dist/tutorial-coordinator/server.mjs` using the coordinator's existing Smithers bundler.
3. Run `bun apps/tutorial-executor/infra/deploy.ts <unique-release-tag> --no-ingress`. It verifies the Kubernetes context, builds and pushes amd64 images, copies only the provider credential into the dedicated secret, applies the manifests, and waits for rollout. The service token remains stable across releases and is never printed.
4. Port-forward the coordinator and perform an authenticated research → plan → implement canary. Verify gVisor, missing service-account mount, isolated pod identities, actual test exit codes and the persisted commit/diff.
5. Add `/__tutorial` to the existing ingress with the same backend shown in `plue/infra/helm/smithers/templates/ingress.yaml` (or rerun the deploy command without `--no-ingress`). Existing paths/TLS are preserved with a resource-version guarded JSON patch.
6. Store `TUTORIAL_SERVICE_URL=https://api.jjhub.tech/__tutorial` through the Worker's optional-var secret input and transfer `TUTORIAL_SERVICE_TOKEN` directly from Kubernetes to its secret input without logging it. Use the Worker's sanctioned deployment path after all app edits stop, preserving its frozen bindings.

The deployment uses the existing `plue-cluster` control-plane service addresses and node-local DNS address in its NetworkPolicy. A cluster migration must update those addresses. Expired pods are removed on the next executor provision. Returning to a completed run reads the coordinator's durable result; continuing a plan after its executor expires must reject its stale base rather than silently applying it to a new repository.

Kubernetes request bodies carry an explicit byte `Content-Length`, including DELETE cleanup requests. Node does not automatically frame DELETE bodies; omitting the length can leave body bytes on a reused connection and make the next request fail with a plain HTTP 400. The coordinator suite exercises repeated DELETE requests through a real keep-alive HTTP server and checks that non-JSON replies report a useful status without exposing upstream content.

Completed and failed coordinator receipts and Flow journals expire after two hours; active runs are retained. The anonymous browser cookie lasts one hour. A real generation probe must succeed before release: listing provider models verifies authentication but does not verify funded generation capacity. The model receives captured example source and test results, with no executor credentials or direct shell tools. Implementation allows two bounded correction attempts. Each model action is capped at 32,000 tokens and two minutes, with provider quota refusals surfaced immediately. A restarted coordinator resumes durable pending runs after the prior engine lease expires.
