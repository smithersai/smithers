# 0036: Page notices reserve space; terminal receipts settle work

2026-10-22. Implements M-48 and decision 0009's requirement that unrelated controls remain usable.

Page notices use `@smthrs/ui`'s existing inline ToastStack above the routed screen, with room for the floating bell. Empty stacks take no space. The three-card cap remains. The 2026-10-25 notification correction keeps all overflow and older notices in the bell, without a `+N` row reserving page space. Model spend alerts are panel entries counted by the bell and delivered through configured email/Telegram channels; they never enter the inline stack. The app shell's conversation stack remains under its header. This is shell infrastructure shared by plugins; no new library or product copy is needed. Catalog entries used: render UI (`@smthrs/ui`), route notifications (`@smthrs/notifications`), and durable flows (`@smthrs/flow`).

Production-like records expose two independent lifecycle gaps. A confirmed engine cancellation is reported as `interrupted`, but chat previously closed only runs refused for changed plans or payloads. The active dispatch now starts the existing idempotent `chat/Close` flow from that terminal receipt. Stop also settles independently of the original tab: `run/cancel` waits for a terminal engine receipt, then calls the existing answer close operation within its durable step. While cleanup is pending, `CancelPending` uses the engine's settlement retry budget; exhausted retries show the existing unavailable refusal. Already successful answers remain successful. This works after reload and on a branch's run page without opening its conversation. No message observer or new execution is needed to reconnect.

A notification can outlive its run-index row. Previously `foldRun` returned zero even after the answer was written `done` or `failed`, leaving the notice `working`, version 1. Missing run metadata now folds the terminal answer into existing live notices, preserving recipients and rechecking current branch access from the remaining conversation scope, failing closed if that scope cannot be read. A streaming answer remains live. When the existing durable expiry observes a missing answer, it fails the remaining run row and folds the notice; when both records are missing, the existing live notice fails. Already settled notices are immutable. Expiry also repairs a missed projection of an already terminal answer. There is no new queue, timer, sweep, or inferred success.

The missing-run repair records `notifications.run_missing` with only run ID and write count, annotates `runs.fold`, and increments the existing routed counters by actual state. Tests use real Postgres records and the real engine, plus browser hit-testing at desktop and phone widths. These fixtures establish the failure mechanisms; they do not establish which occurred in the original production account.
