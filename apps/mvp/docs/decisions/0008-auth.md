# 0008: Auth: one GitHub identity, open by default, carried by every flow

Status: sign-in with the GitHub App is built ([sign-in](../features/sign-in.md)); the device flow for the TUI and CLI, grants and the visitor cookie are not ([not built yet](../features/sign-in.md#not-built-yet)). Will's answers are in §11 (2026-10-19). Roles and permissions are `0007-roles-and-tags.md`, designed in parallel; sandboxes and the secrets proxy are `0005-sandboxes-secrets-and-the-forge.md`, not yet written. This record decides who is acting and how that fact travels. 0007 decides what they may do. §6 is the interface between them.

## Decision

1. **Every request and every step has one `Actor`:** a principal (visitor, guest or person), the session or grant it came through, and, when an agent, flow or sandbox acts for that principal, who is acting (RFC 8693's `act` [15]). A person is keyed by their GitHub numeric id, never their login.
2. **Better Auth 1.7.7 through `@alchemy.run/better-auth` 2.0.0-beta.83** [4], on the same Neon Postgres through Hyperdrive, in schema `auth`. Plugins: `anonymous` [1], `device-authorization` [2] and `bearer` with `requireSignature: true`. Cookie cache off, telemetry off.
3. **People sign in through the Smithers GitHub App's user authorization** (PKCE S256, state, 8-hour `ghu_` tokens with 6-month single-use `ghr_` refresh tokens [6][7][10]). The same App imports repositories (M-46). No separate OAuth App ([Q1](#11-wills-answers-2026-10-19)).
4. **Open by default.** A visitor reads and explores with no row anywhere. The first ask creates a guest identity. Sign-in is needed only for what §1's table lists.
5. **Signing in from a guest session merges the guest into the person,** new or existing, through one durable flow, `auth/MergeGuest`. The guest's conversations and queued asks carry over; nothing is copied between devices.
6. **Each client holds its own revocable session** under the one person: a cookie on the web, a device-flow bearer token in the TUI and CLI. Agents, flows and sandboxes never hold a session; they hold grants.
7. **The server stamps the actor.** A run's start intent records the actor and a grant; the engine journals it and provides it to every step as `CurrentActor`. No credential enters a journal, payload, step key or log line.
8. **Electric shapes are authorized on every request.** The proxy derives `table`, `where` and `columns` from the actor and the conversation; the browser names only the conversation and its sync position.
9. **A delegated capability set is an intersection:** what the grant names, what the person holds (0007), and never the non-delegable set (approve, merge, sign-in, device approval, granting).
10. **Abuse: alerts on token spend first, then admission limits** as the first step of the ask flow, then Turnstile on guest creation. No gate on reading or on the first page.

## Why

- **The library fits the stack exactly.** `@alchemy.run/better-auth` is Alchemy's Effect-native wrapper, pinned to the same `alchemy` 2.0.0-beta.83 the app runs, with a Hyperdrive layer and endpoints exposed as Effects [4]. Better Auth already ships each piece this design needs: anonymous users with an `onLinkAccount` hook [1], an RFC 8628 device flow [2], bearer tokens, a GitHub provider with PKCE and refresh, Turnstile [19] and encrypted OAuth tokens. The backend's equivalent is about 8,500 lines of non-test Go (sign-in, sessions, OAuth, CSRF and credential middleware), which cannot run on Workers.
- **Reading its 1.7.7 source [5] found four gaps; each has a setting and a test.** It stores the raw session token in the row (`createSession`), so a database read must not sign anyone in: cookies are HMAC-signed, and `requireSignature` makes bearers signed too. Its device flow returns an unsigned token, so an `after` hook on `/device/token` signs it. It names cookies `__Secure-`, not `__Host-`, so another origin under our registrable domain could set one: previews and rendered views live on a separate registrable domain. It records IP and user agent per session: `disableIpTracking` is on, and the devices list shows a client name instead.
- **One GitHub App, not an OAuth App.** GitHub prefers Apps [8]. An App's user token holds only what both the person and the App hold [6], so a leak or a confused agent cannot exceed the App. M-46 needs the App anyway, and the backend already signs in this way (`packages/backend/internal/services/github_app_credentials.go:400`).
- **The CLI and TUI sign in to Smithers, not to GitHub.** A device flow works over SSH, on the Mac mini and inside a sandbox, where a loopback redirect [14] cannot reach a browser. The CLI never holds a GitHub token, and each device is a revocable session in one list.
- **Sessions live in Postgres, read on every request.** KV can take 60 seconds or more to show a revocation in other locations [17], and Better Auth's cookie cache keeps revoked sessions alive until it expires [3].
- **Abuse order follows Will's 2026-10-19 ruling** (`apps/mvp/docs/todo.md`): open use is intended, so the first control tells a person; gates come after we know the spend.
- **Prior art kept from the backend** (`packages/backend/internal/`): session keys hashed at rest (`middleware/auth.go:907`), a cross-replica lock for single-use refresh tokens (`services/auth.go:287`), credential kinds for agent runs (`middleware/run_credential.go`), a spend kill switch (`guest/spend.go:54`), and network buckets for IPv6 (`guest/http.go:289`).

## Consequences

- **New dependencies:** `better-auth` 1.7.7 (2026-09-30) and `@alchemy.run/better-auth` 2.0.0-beta.83 (2026-10-12), both past the 7-day rule, alone at the bottom of the stack. Better Auth's `pg` pool joins `@effect/sql-pg` in the Worker; both use the one Hyperdrive binding.
- **Better Auth's own writes (users, sessions, accounts, device codes) run in its handlers.** An OAuth code is single-use and request-bound, so a durable retry cannot redeem it twice. Every action identity starts beyond that (merging, granting, revoking, refreshing a GitHub token) is a flow. The `durable.every-action-is-a-flow` rule gets this one named exception.
- **The single shared conversation ends.** Today every visitor reads every message. `conversations` gets an owner, and `messages` gets `conversation_id`. The existing rows move to one archived conversation no visitor can read.
- **SDK changes:** `@smthrs/flow` gains `Actor` and `CurrentActor`. `@smthrs/capability` gains the `Authorize` service that 0007 implements. `ShapeProxy.make` (`@smthrs/effect-electric`) gains an `authorize` hook. `OtlpRelay.serve` (`@smthrs/observability`) requires an actor.
- **GitHub becomes the second scripted seam** in unit tests of the callback. End-to-end tests sign in with the real `codeplanesmithers` test account. `apps/mvp/AGENTS.md` names the model as the only scripted seam, so this needs the lead's sign-off.
- **Two sign-in implementations exist** while the Go backend serves `apps/app`. Retiring one belongs to the hosting decision.

## 1. Identity model

| Principal | Created | Row | Can |
|---|---|---|---|
| Visitor | first `/api/*` response | none: `__Host-smithers_visitor` (`smithers_visitor` on plain http, M-28) = `v1.<128-bit id>.<HMAC>`, 1 year | read public repositories, docs and the launcher; send telemetry |
| Guest | first ask, after Turnstile (P2) | `auth.user` with `isAnonymous` | everything a visitor can, plus its own conversations, within guest limits |
| Person | GitHub sign-in | `auth.user` + `auth.account` (`github`, numeric id, tokens encrypted with `encryptOAuthTokens`) | everything else 0007's roles allow |

Sign-in is needed to: import or open a private repository, create branches, sandboxes, TODOs, issues or pull requests, hold or use a secret, run a repository flow that writes, join a team, use the TUI or CLI beyond public reads (Turnstile needs a browser), delegate to an agent, and go past guest limits. The rule: anything that acts on GitHub as a person, touches a secret, writes to a repository or spends past the guest budget.

```ts
// @smthrs/flow: generic; the app defines principal kinds.
interface Actor {
  readonly subject: { readonly kind: string; readonly id: string } // "visitor" | "guest" | "person" in this app
  readonly via: { readonly kind: "session" | "grant"; readonly id: string }
  readonly act?: { readonly kind: "agent" | "flow" | "sandbox"; readonly id: string } // RFC 8693 `act`
}
```

A **grant** is a row: `{ id, subject, act, capabilities, resources, expires_at, revoked_at, parent_grant }`. Its token, when one is issued, is `smithers_<kind>_<256-bit random>`, stored as a SHA-256 digest; the prefix lets the redactor and credential scanner find it.

## 2. Sessions and tokens per client

| Holder | Credential | Kept in | Lifetime | Ended by |
|---|---|---|---|---|
| Browser (guest or person) | signed session cookie: HttpOnly, Secure on https, SameSite=Lax, Path=/, no Domain | cookie jar | 30 days, renewed daily on use | sign out, devices list, merge, GitHub revocation |
| TUI, CLI | signed session token, `Authorization: Bearer` | OS keychain; `0600` file fallback (today's `Session.ts`) | 30 days, renewed daily on use | `smthrs auth logout`, devices list |
| Flow run, agent turn | grant id in the journal; a 15-minute token, minted only when a step calls Smithers from outside the Worker | memory only | the run's deadline, at most 24 h | grant revoked or expired; checked at each step with an outside effect |
| Sandbox | `smithers_sbx_` token bound to sandbox id, generation, branch and grant | sandbox environment; reaches only the Smithers API host | 1 h, renewed by the host | sandbox stop, grant revoked |
| Person on GitHub | `ghu_` + `ghr_` | `auth.account`, encrypted | 8 h / 6 months [7] | the `github_app_authorization` revocation webhook [6]: revoke every session and grant |
| App on GitHub | `ghs_` installation token per step, `repository_ids` + `permissions` [11] | memory only | 1 h | expiry |

Signing out ends a session, not the person's runs. Revoking a person (0007) or pressing Revoke all revokes their grants, and each run stops at its next step check.

## 3. Sign-in flows

**Web.** Sign in with GitHub is a button the person presses, never an automatic redirect. Agents may show the button and never press it: sign-in is on the agent-parity list of user-only gestures.
1. `POST /api/auth/sign-in/social { provider: "github", callbackURL }`, with `callbackURL` a same-origin path (Better Auth `trustedOrigins`).
2. Redirect to GitHub with the App's client id, `state` and an S256 `code_challenge`. Better Auth binds `state` to this browser with a signed cookie; `skipStateCookieCheck` stays off.
3. `/api/auth/callback/github` exchanges the code with the client secret and verifier, then upserts the person by GitHub numeric id.
4. If the browser held a guest session, `onLinkAccount` starts `auth/MergeGuest` (§4). `disableDeleteAnonymousUser` is on, so the flow, not Better Auth, deletes the guest last.
5. Better Auth sets the new session cookie and revokes the guest session; the browser returns to the same page.

**TUI and CLI (device flow).** `smthrs auth login` posts `/api/auth/device/code` (`expiresIn: "10m"`, 8-character user code, `interval: "5s"`). It prints the code and `/device`. On the web, the person signs in if needed, types the code, and sees the client, device name, coarse location and time before choosing Approve or Deny, as RFC 8628 §5.4 advises against remote phishing [13]. The CLI polls `/api/auth/device/token`, honouring `slow_down`, and stores the signed token in the keychain. Wrong codes are rate-limited per session and network (§5.1 [13]).

**Import and installation (M-46).** Repository access is checked with the person's `ghu_` token; a 404 shows the notice M-46 names. Installation coverage is checked with the App's JWT. The installation path returns to the setup URL, whose `installation_id` is never trusted: it is verified against the person's `/user/installations` [12].

**Agents never sign in.** They run under grants (§5).

## 4. Upgrading anonymous use

The guest's data is already on the server, owned by the guest. Sign-in changes the owner. It never copies messages.

1. **Callback.** `onLinkAccount({ anonymousUser, newUser })` starts `auth/MergeGuest` keyed by the guest id. Its idempotent caller effect ([HOST-PLAN] decision 2) sets `guest.merged_into = person` before the cookie is issued.
2. **No race.** Until the flow ends, `Authorize` treats anything owned by a guest whose `merged_into` is the actor as the actor's. An ask sent a millisecond after sign-in is accepted.
3. **Flow steps.** Move `conversations.owner` from the guest to the person; revoke the guest's sessions and grants; delete the guest row. A person who already had conversations gets the guest's beside them. Ids are UUIDs, so nothing collides.
4. **Device.** After the redirect, boot sees a new principal. It opens that principal's OPFS database (decision 0002: one database per account) and syncs the person's shapes. The IndexedDB outbox keeps draining under the new cookie. Once the outbox holds no guest ask and the moved rows have arrived, the guest database is deleted.
5. **Offline.** Asks queued before sign-in stay in the outbox. The outbox sends them once, under whichever identity the browser holds when it next reaches the server.
6. **Sign out.** Drain the outbox if online, else show how many asks will be discarded, then wipe this principal's OPFS database and outbox (decision 0002). The page continues as a visitor; a new guest is created only at the next ask.

## 5. How identity reaches flows, shapes, sandboxes and secrets

- **Flows.** Starting a run, the server resolves the request's `Actor` and mints a run grant: the flow's declared capabilities, intersected with what the person holds, expiring at the flow's `Deadline`. The start intent `{ flow, executionId, payload, actor }` is journaled, and `CurrentActor` comes from the journal on every replay. A payload field named actor is never read. Each step with an outside effect calls `Grants.live(grantId)`. Child runs (agent tool calls, remote delegation from a browser flow) get a grant that is a subset of their parent's.
- **Model calls.** `ModelStep` keys exclude credentials ([HOST-PLAN] decision 6). Spend is recorded per subject for §7.
- **GitHub.** One `GitHubTokens` service mints installation tokens per step with only the repositories and permissions that step needs [11]. It refreshes a person's token in `github/RefreshUserToken`, keyed by account and refresh-token digest, so concurrent refreshes collapse into one execution: a used refresh token dies [7].
- **Electric shapes.** `/api/shapes/messages?conversation=<id>&offset&handle&live`. The proxy calls `Authorize.check(actor, conversation:read:<id>)`, then sends Electric `where conversation_id = $1` with `params`, a fixed column list, and only `offset`, `handle`, `live` and `cursor` from the browser [21]. It answers `Cache-Control: private` and `Vary: Cookie, Authorization`. A long poll re-authorizes on every request, so a revocation ends sync within one poll. The conversation list is a second shape, `where owner = $1`; team ownership waits for 0007.
- **Asks.** `POST /api/questions` names its conversation. ChatApi authorizes it and creates the conversation on the first ask; it never takes an owner from the browser.
- **Device commands** (an agent calling a tool on a person's device, feature 1). A command targets a session id. Its receipt is accepted only from that session.
- **Sandboxes (0005).** A sandbox gets its `smithers_sbx_` token and secret placeholders. The egress proxy authenticates each request by the provider's identity for that sandbox plus the token, resolves the grant, and injects only secrets the grant binds to that repository, branch, sandbox generation, flow and destination. A sandbox id the guest sends proves nothing.
- **Secrets.** Using a secret is the capability `secret:use:<name>`; managing one needs a person and 0007's role. A secret's value never appears in an actor, grant, token, journal, log, span or metric (M-47).
- **Telemetry.** `/api/telemetry` accepts an export only with a session or a valid visitor cookie, rate-limited per visitor. Inbound `traceparent` is honoured only on such requests. A visitor id proves nothing about a person; it gives limits and records a key.

## 6. The interface with roles (0007)

```ts
// @smthrs/capability; 0007 provides the layer.
class Authorize extends Context.Service<Authorize, {
  readonly check: (actor: Actor, capability: Capability) => Effect.Effect<void, PermissionDenied>
}>()("@smthrs/capability/Authorize") {}
```

- **0008 provides** `Actor`, the session and grant lifecycle (`Grants.mint`, `Grants.live`, `Grants.revoke`) and principal events (`merged`, `deleted`, `githubRevoked`) that 0007's memberships follow.
- **0007 provides** `Authorize`, roles, tags, branch protection and the capability names. Until it lands, P1 ships an owner-only policy behind the same tag.
- **The delegation rule holds in both:** with `act` set, `check` passes only if the subject passes, the grant names the capability, and the capability is not non-delegable.

## 7. Abuse controls

1. **Alerts (P0).** `smithers_chat_tokens` gains `model` and subject `kind` attributes, never ids. An alert at Will's threshold reaches Will ([Q3](#11-wills-answers-2026-10-19)). The documented actions are three operator flows: pause guest asking, block a network, lower a budget. Each is read on every admission.
2. **Admission (P2).** `chat/Admit`, the ask flow's first step, reserves the request's maximum output tokens against three budgets in Postgres: per subject per day, per network per day (a keyed hash of the IPv4 /24 or IPv6 /48 from `CF-Connecting-IP`), and the deployment per day. `chat/Settle` books the actual tokens. A refusal is 429 with `retry_at`, and the ask stays in `unsent` (decision 0002, item 5).
3. **Edge pre-filter (P0).** The Workers Rate Limiting binding, per network, on asks, guest creation and device codes. It is approximate and per location by design [18], so it bounds bursts and never does accounting.
4. **Turnstile (P2)** guards guest creation only, invisibly: Better Auth's `captcha` plugin with `cloudflare-turnstile`, its `endpoints` set to `/sign-in/anonymous` [19]. Validation is server-side and tokens are single-use. Supabase gives the same advice for anonymous users, which inflate the database [20]. If it fails, the ask waits in `unsent` beside a Sign in button.

## 8. Threat model

| Threat | Control | Proved by |
|---|---|---|
| Open model spend | §7 alerts, pause, budgets, Turnstile | E9, E10 |
| Reading someone else's conversation | server-set `where`; per-request authorization; `Vary`; UUID ids grant nothing | E4 |
| Login CSRF grafting a guest's conversation into an attacker's account | `state` and PKCE bound to the starting browser | E6 |
| Session theft from a database read | signed cookies, `requireSignature`, grant tokens stored as digests | U2 |
| XSS or cookie tossing | HttpOnly cookies; generated HTML and previews on a separate registrable domain with no app cookies | E11; feature 3's frame tests |
| CSRF on writes | SameSite=Lax plus an `Origin` / `Sec-Fetch-Site` check on non-GET routes [16] | U3 |
| Silent sign-in (M-46) | button only, no auto-redirect, agents never press it | E1 |
| Device-code phishing | typed code, device details, 10-minute expiry, attempt limits [13] | E7 |
| Agent confused deputy or prompt injection | grants are intersections; non-delegable set; per-step liveness | U4, E8 |
| Sandbox steals a credential | placeholders only; proxy injects; token bound to generation (0005) | 0005's suite |
| GitHub token leak | encrypted at rest; per-step scoped installation tokens; single refresh path | U5 |
| Spoofed installation callback | verified against `/user/installations` [12] | U6 |
| Forged telemetry or traces | session or visitor binding; per-visitor limits | U7 |
| A revoked session keeps syncing | re-authorization on every shape request | E5 |

## 10. Tests

All e2e tests run on the real local stack (`alchemy dev`, compose Postgres and Electric) and record video. Unit tests use real Postgres.
- **E1:** signed out, a visitor asks, reloads and reads the answer; no request reaches GitHub until the button is pressed.
- **E2:** sign in from a fresh browser; the person is keyed by GitHub id; a second browser with the same account sees the same conversations.
- **E3:** a guest queues three asks offline, signs in, comes back online: each ask is sent once, answered, and shown on the person's other device; the guest database is gone.
- **E4:** isolation: person B cannot read A's conversation by shape (403), by ask (403) or by guessed id; a guest cannot read another guest's.
- **E5:** revoke device B from device A; B's next shape poll is 401, and B is a visitor.
- **E6:** a callback completed in another browser context signs nobody in and merges nothing.
- **E7:** device flow: approve, deny, expired code, wrong code limits, `slow_down`.
- **E8:** an agent grant cannot merge, approve or mint a grant; a revoked grant stops the run at its next step.
- **E9 and E10:** a guest over budget gets 429 and the ask stays in `unsent`; the deployment budget pauses guests while people keep asking.
- **E11:** cookie attributes on http and https, WebKit included (a Secure cookie on http loopback is dropped there).
- **U1 to U7:** merge idempotence and the merged-into race; bearer refused without a signature; cross-site POST refused; capability intersection, including the non-delegable set; refresh collapse under concurrency; installation-id spoof; telemetry without an actor.
- **Sentinel:** session tokens, `ghu_`, `ghr_`, `ghs_`, device codes, Turnstile tokens and grant tokens never reach exported telemetry, journals or step keys.

## 11. Will's answers (2026-10-19)

1. **Sign in through the Smithers GitHub App.**
2. **A signed-out person's data stays in their browser and is never synced to our backend.** Features that can't run browser-first are disabled until sign-in. **That includes asking Smithers:** a signed-out person can't ask yet, enforced in the straightforward way (Will may revisit). Every model call therefore stays a durable flow with no stateless exception. There are no guest rows on the server; on sign-in, local data uploads through the outbox. The guest-row, `auth/MergeGuest` and `auth/ExpireGuest` parts of this record need revising to fit.
3. **Alert on any use.** With no users yet, any model spend at all alerts Will. Thresholds are configured as usage grows.
