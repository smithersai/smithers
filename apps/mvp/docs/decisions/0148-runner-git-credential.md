# 0148: A runner reads a private repository with the App's token

Status: accepted
Date: 2026-11-02

A runner (decision 0136) checks out a TODO's base from a local jj mirror it fetches from GitHub. For a private repository the fetch needs a credential, and the runner had none: every private repository whose TODOs ran on a runner failed `workspace`. The issue-tracking proof hit it on its private repository (docs/features/work-links.md#the-proof). The runner's pull request already goes through the host: the runner sends its change, and the App writes the branch and the pull request (docs/features/agent-runners.md), so only reading was missing.

The first version (55003bd3) was reviewed before it served a request, and the route was turned off (ee3bd133). The fixes below are built and tested; the route stays off in production (`GIT_CREDENTIAL_ON` in `worker/runners/Api.ts`) until their review passes, answering `404`, which the runner reads as no credential. The review's blocking finding: registering a runner didn't prove the registrant could read the repository. Where Smithers had recorded no App installation, the Admin route took the deployment-wide role, so a deployment Admin could register a runner on a private repository they can't read, and once the installation was recorded the runner would claim its jobs and be handed its credential.

A second round of fixes (5fc33348) was reverted (fe0a66f3) after Codex Astra's review, except its migration 0089, which was published. That review found: 0089's backfill authorized runners the old route's fallback admitted (its role also fell back to the deployment's on `not_found`, a repository outside `GITHUB_ALLOWED_REPOSITORIES` included); a flow admitted that way and resumed after a deploy was stamped authorized; git configuration an agent writes in the mirror (an SSH remote with `core.sshCommand`, a `credential.helper`, a proxy, a CA) still ran with the credential; a failed mint gave back a snapshot that could erase a later success; a credential GitHub couldn't mint before the checkout existed ended the job `machine_lost` on its next generation; and reclaiming a held job skipped the checks a claim makes. This decision records the fixes to all of them.

## Decision

1. **Registration proves access to the repository.** Registering a runner, naming an agent or turning overflow on needs the App's recorded installation on the repository and the Admin role GitHub gives there; the deployment's own role never stands in for it. Every Admin action on a repository's runners, agents and overflow carries one fence: the route reads the body before the role, and the flow's transaction checks the authority it was admitted by again under lock (the repository's role row with `RepoRoles.holds`, or the sign-in session on the deployment's own repository), the fence's own five-minute expiry, and the generations it was admitted against (the runner's or agent's, which survive a removal, and the repository's coding selection's), all after the resource's lock and by the clock right before the write, so a body held open, a flow run late, two first registrations at once, or an action started before fences writes nothing beyond the first, and its receipt, which a replay answers with, says why (`authorization_expired`, `superseded`). Only such a registration marks the runner `repo_authorized_at`: the route says so in the flow's payload (`repoAuthorized`), so an `admin/AddRunner` or `admin/SetOverflow` started before the route proved the role, and resumed after a deploy, registers its runner unauthorized. Only an authorized runner claims a job, reclaims one it holds (`403 not_authorized` otherwise; the runner logs that it needs re-registration) or is handed a credential, and a claim or reclaim also needs the recorded installation and the token the runner authenticated with. A runner holding a job is fenced the same way: its heartbeat (lease and steers), settlement and transcript events are refused `403 not_authorized` unless it is current. Every such route holds that in its own transaction: it locks the runner's row, then its repository's installation row, `FOR SHARE`, before the job's, so a revocation that commits while the operation waits is seen, and one that comes later waits until the operation (the transcript's append, the steers handed out, the credential counted) commits. A work-link post reads its body first and writes in a transaction that holds the runner the same way. The runner treats a `403`, and a `401` (its token rotated or retired), as a suspension, not an end: only an authenticated answer that the claim no longer holds (`held: false`) ends the job's work. A refused heartbeat stops the agent and keeps the checkout and the session checkpoint; the runner beats on, and the first heartbeat taken again resumes the session from its checkpoint, as after a restart, including a restart with a new token. A suspended job still ends at its deadline (`timeout`), on a stop, or on `held: false`, so it never holds the runner's capacity past those. A refused settlement keeps the outcome and the checkout and asks again, 1 second doubling to a minute, until the host takes it, the claim is lost, or 10 minutes past the job's deadline (by when the host has ended the job itself); the bound is the journaled deadline, so it holds across restarts. A refused credential is waited out like one the host can't issue now, and the credential route answers `403 not_authorized`, never `409 not_held`, when the runner stops being current while its reservation waits or while GitHub mints; `409` means only that the claim doesn't hold. One thing still reaches a runner the host no longer takes: a Stop on its own claim. Its heartbeat for that key and claim ends the job `Cancelled` on the host, keeps the claim as `stopped_claim` (migration `0095_runner_reauthorization`), and answers `403 { cancel: true }`, again to every later heartbeat with that key and claim, so an answer lost on its way is said again. The runner stops the job, gives up settling it, and frees its slot; the answer grants no lease, steers or other work. A runner whose token was rotated or that was retired since it claimed the job (the host keeps the claiming token's SHA-256 as `claimed_token_sha256`: migration `0095_runner_reauthorization` fills it in for jobs claimed before it, and a heartbeat sets it where it is still missing) hears the same Stop as `401 { cancel: true }` on that job's heartbeat, and every other request of its old token is `401`. Only that answer lets the runner give up a refused settlement or refused transcript events early: a Stop heard on a heartbeat the host took is the runner's to settle, retried like any outcome. Each request's bound covers its answer's body; a refusal's body is read for `cancel` for at most 5 seconds, and one that doesn't arrive whole or parse is a plain refusal. A claim or reclaim ends the runner's own claimed jobs past their deadline and the host's settlement grace (`timeout`) in its transaction, whether or not the job store's probe ran, so a job a runner gave up settling is never handed back and holds no slot. Transcript events refused so stay in the spool. Nothing of the job's execution ends for it, so once the runner is registered again the job goes on where it stopped. Every other route that takes a runner's token takes it only on the same terms: posting an issue's work links (`403 not_authorized` otherwise) and reading the repository's issues list (the refusal anyone without access gets). No earlier registration is trusted: migration `0095_runner_reauthorization` clears `repo_authorized_at` on every runner, whatever migration 0089's backfill set, since that backfill inferred authorization from `github_repositories.checked_at` and the old route's fallback admitted registrations it can't tell apart. Every runner is registered again ([agent-runners.md](../features/agent-runners.md#registering-a-runner-again)).
2. **The host mints, per job, a read-only token for one repository.** `POST /api/runners/git-credential { key, claim }` with the runner's own token answers `{ remote, username, password, expiresAt }` only while that runner, unremoved and authorized, holds that job (`claimed`, before its deadline), only for the repository the runner is registered on, whatever the task names, and only where the installation is already recorded (minting would otherwise discover and record it). The token is the App's installation token minted with `repositories: [<name>]` and `permissions: { contents: "read" }`: it reads that repository's contents and nothing else, and it can't write.
3. **Issuance is bounded per reservation and checked again after minting.** One mint per job is in flight at a time. A mint starts at least 30 seconds after the job's last one started, issued or failed, after the wait a failed one set (30 seconds, or GitHub's own `retry-after` when longer), and under 3 issued in the hour; else `429` with `retry-after`. The request reserves its mint under its own id, in one transaction on the job's row, and only that id finalizes or releases it. A success is counted, after the runner's, installation's and job's rows are locked, in a statement that checks the hold again against the time it runs (`clock_timestamp()`, so a lock waited on across the deadline issues nothing) (a job settled, a runner retired, unauthorized or uninstalled, or a deadline passed meanwhile), and a credential that statement doesn't count is revoked (`DELETE /installation/token`) and never delivered. A failure answers `503` with its wait and spends nothing of the hour. A mint is given up after 20 seconds; a reservation older than 60 seconds belongs to a request that died, and another request may take it over, whose old request's late answer is then revoked.
4. **The runner asks only when it must, and reuses the answer.** The runner asks while it holds the mirror's lock, and only when the mirror must clone or fetch the base. It reuses a credential for the same claim until 10 minutes before its `expiresAt` (50 minutes after minting; GitHub ends it at the hour), and concurrent asks for one claim reach the host once.
5. **Only `404` means "fetch without one", and a host that can't answer now costs no generation.** A public repository, a host without the App, or the App not installed there answers `404`, and the runner fetches as before. On `429`, `5xx` or no answer the same claim waits (the host's wait, else 15 seconds doubling to 5 minutes, at most half the time left before the deadline) and makes the checkout again, until the deadline passes (`timeout`), a stop or a lost claim, each of which also ends an attempt in progress, its wait for the mirror and a fetch that stalls included: every command that makes a checkout, discarding an incomplete one included, runs in a process group of its own, killed whole and waited for before the mirror is let go: no `Retryable`, so no generation and none of the agent's restarts are spent before any agent ran. Before it first tries, the runner marks the checkout as being made (`<checkout>.provisioning`). A provisioning that fails keeps the mark until the settlement forgets the checkout; one that succeeds removes it, written through to disk with its directory entry, then records, outside `work/`, that an agent is about to run in it (`<state>/started/<checkout>`), each written through to disk. On a claim handed back after a restart: a marked checkout is incomplete whatever its directory holds, so it is discarded and made again, unless the started record is there too (a machine that lost the mark's removal), when the checkout is kept and the mark goes; a missing checkout is `machine_lost` only where that record or the session checkpoint says an agent was to run in it; otherwise (the runner died after the host recorded the claim but before it wrote anything) the checkout is made. Any other refusal fails `workspace` without fetching.
6. **It is never on a command line, in a file or in a log, and it never runs in the mirror.** The mirror's git and jj configuration is the agent's to write, so the one git command that carries the credential runs elsewhere: the git on the runner's own `PATH` fetches the credential's exact remote, given on its command line (HTTPS, or HTTP to loopback for tests; nothing else is fetched with one), into a bare repository under the runner's state directory (`<state>/fetch/<16 hex>.git`). The state directory's real path is resolved once and each of its components checked to be a real directory on every use; the store and `fetch/` are made real directories of the runner's user, a link there is removed rather than followed, and a store holding any link or anything not the runner's own (its objects, `objects/info` or refs included) is removed whole and made anew. Before each fetch the runner rewrites that repository's configuration whole (no hook, no file-system monitor, no gc, TLS verified, only the remote's own transport) and removes its hooks, alternates and any pointer to another repository. The command reads neither git's global nor its system file and gets none of the runner's `GIT_*` (tracing, `GIT_CURL_VERBOSE`, configuration from the environment, `GIT_SSH*`, `GIT_ASKPASS`, `GIT_SSL_NO_VERIFY`) or `SSH_ASKPASS`; the credential reaches it as `GIT_CONFIG_COUNT` with `http.<origin>/.extraheader`, as `actions/checkout` does. The mirror then fetches from that repository with no credential and runs no hook. jj runs with an empty configuration directory this process made, and with `--config git.executable-path=<the git on the runner's own PATH>`. The route's record names the job and the outcome, never the token; the answer is `Cache-Control: no-store`.

## Consequences

- A runner token yields read access to its repository's contents for the length of a job it holds, up to 3 tokens an hour. A runner already receives that repository's code through its jobs, and an Admin retires a runner at once (`DELETE .../runners/<name>`). A token delivered before the job ended stays usable until GitHub's hour runs out; only one minted for a request that is then refused is revoked.
- **The agent shares the runner's trust (decision 0136).** An agent runs as the runner's user, unsandboxed. It can't read the token from its own environment or checkpoint, and no configuration it plants in the mirror (git or jj: an executable path, a remote, an SSH command, a credential helper, a proxy, a CA, a URL rewrite, an include, a hook) reaches the credentialed command. It does not stop an agent that acts as that user against the runner itself: reading the runner's process memory or the credentialed command's environment while it runs, replacing the `git` on the runner's `PATH`, or writing the fetch store between the runner's rewrite and git's read. On a machine where that matters, run the agent as another user or in a sandbox (decision 0136 records this as debt).
- Migration `0095_runner_reauthorization` waits at most 5 seconds for a lock and runs no statement past 60 seconds, then puts the transaction's own limits back: a deploy that meets a long transaction on `runners` or `agent_jobs` fails and runs again rather than queueing the runner routes behind it. It rewrites no runner already clear.
- **Every runner stops claiming at the deploy that runs migration `0095_runner_reauthorization`, until an Admin of its repository registers it again** (the same `PUT`, the same `tokenSha256`; an overflow is turned on again with its `PUT`). Its queued jobs wait for it. A job it holds is suspended: its next heartbeat is refused, so it stops the agent and keeps its work; registered again before the job's hours are up, the runner resumes it, else the job ends `timeout`. The fleet shows it `Needs re-registration`, the audit flags it `needs_registration`, and the runner logs the hint on every refused claim. A machine posting work links with `ops/work-links/link.mjs` gets `403 not_authorized` until its runner is registered again. Runners an end-to-end run registers are registered on each run, so they are unaffected.
- A deploy key or a person's token on the runner machine stays possible, and is no longer needed. A fetch without a credential keeps the runner's own git setup.

Libraries: none new. The App's installation tokens (`worker/github/Tokens.ts`), git's own `GIT_CONFIG_*` environment.
