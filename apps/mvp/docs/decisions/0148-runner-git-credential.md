# 0148: A runner reads a private repository with the App's token

Status: accepted
Date: 2026-11-02

A runner (decision 0136) checks out a TODO's base from a local jj mirror it fetches from GitHub. For a private repository the fetch needs a credential, and the runner had none: every private repository whose TODOs ran on a runner failed `workspace`. The issue-tracking proof hit it on its private repository (docs/features/work-links.md#the-proof). The runner's pull request already goes through the host: the runner sends its change, and the App writes the branch and the pull request (docs/features/agent-runners.md), so only reading was missing.

The first version (55003bd3) was reviewed before it served a request, and the route was turned off (ee3bd133). The fixes below are built and tested; the route stays off in production (`GIT_CREDENTIAL_ON` in `worker/runners/Api.ts`) until their review passes, answering `404`, which the runner reads as no credential. The review's blocking finding: registering a runner didn't prove the registrant could read the repository. Where Smithers had recorded no App installation, the Admin route took the deployment-wide role, so a deployment Admin could register a runner on a private repository they can't read, and once the installation was recorded the runner would claim its jobs and be handed its credential.

## Decision

1. **Registration proves access to the repository.** Registering a runner, naming an agent or turning overflow on needs the App's recorded installation on the repository and the Admin role GitHub gives there; the deployment's own role never stands in for it. Such a registration marks the runner `repo_authorized_at`, and only such a runner claims a job (`403 not_authorized` otherwise; the runner logs that an Admin must register it again) or is handed a credential. A claim also needs the recorded installation. Runners registered before are backfilled only where their repository's installation record is older than the registration, since the old route took the role GitHub gave where an installation was recorded. `github_repositories` keeps no time the installation was recorded; `checked_at`, which every write of that row sets, is the best there is, and a row written after the runner was added proves nothing.
2. **The host mints, per job, a read-only token for one repository.** `POST /api/runners/git-credential { key, claim }` with the runner's own token answers `{ remote, username, password, expiresAt }` only while that runner, unremoved and authorized, holds that job (`claimed`, before its deadline), only for the repository the runner is registered on, whatever the task names, and only where the installation is already recorded (minting would otherwise discover and record it). The token is the App's installation token minted with `repositories: [<name>]` and `permissions: { contents: "read" }`: it reads that repository's contents and nothing else, and it can't write.
3. **Issuance is bounded and checked again after minting.** One job's runner is handed a credential at most every 30 seconds and 3 an hour; past that the route answers `429` with `retry-after`. The check and the reservation are one transaction on the job's row, so concurrent requests mint once. A mint GitHub can't make gives the reservation back. After minting, the route checks the hold again: a job settled, a runner retired or a deadline passed meanwhile gets `409`, and the minted token is revoked (`DELETE /installation/token`).
4. **The runner asks only when it must, and reuses the answer.** The runner asks while it holds the mirror's lock, and only when the mirror must clone or fetch the base. It reuses a credential for the same claim until 10 minutes before its `expiresAt` (50 minutes after minting; GitHub ends it at the hour), and concurrent asks for one claim reach the host once.
5. **Only `404` means "fetch without one".** A public repository, a host without the App, or the App not installed there answers `404`, and the runner fetches as before. `429`, `5xx` or no answer settles the job `Retryable`, with the host's wait. Any other refusal fails `workspace` without fetching.
6. **It is never on a command line, in a file or in a log.** The runner gives it to git through the command's own environment (`GIT_CONFIG_COUNT`, `http.<origin>/.extraheader`, as `actions/checkout` does), for that one command. That command's environment drops the runner's `GIT_TRACE*`, `GIT_CURL_VERBOSE`, `GIT_CONFIG*`, `GIT_EXEC_PATH` and `JJ_*`, sets git's tracing off (which wins over git's global and system files; trace2 reads no repository's), reads no global or system git file, runs no hook (`core.hooksPath`), verifies TLS and drops pinned addresses. jj runs with an empty configuration directory this process made, and with `--config git.executable-path=<the git on the runner's own PATH>`, which wins over the mirror's jj configuration. The route's record names the job and the outcome, never the token; the answer is `Cache-Control: no-store`.

## Consequences

- A runner token yields read access to its repository's contents for the length of a job it holds, up to 3 tokens an hour. A runner already receives that repository's code through its jobs, and an Admin retires a runner at once (`DELETE .../runners/<name>`). A token delivered before the job ended stays usable until GitHub's hour runs out; only one minted for a request that is then refused is revoked.
- **The agent shares the runner's trust (decision 0136).** An agent runs as the runner's user, unsandboxed. It can't read the token from its own environment or checkpoint, and the hardening above stops the planted-configuration routes the review found: a jj `git.executable-path` set with `jj config set --repo` from its checkout, a hook in the mirror's git store, ambient tracing. It does not stop an agent that acts as that user against the runner itself: reading the runner's process memory, replacing the `git` or `jj` on the runner's `PATH`, or editing git configuration this hardening doesn't override (a CA bundle or proxy in the mirror's git store). On a machine where that matters, run the agent as another user or in a sandbox (decision 0136 records this as debt).
- A runner registered before this decision whose repository's installation record isn't older than it stops claiming until an Admin registers it again (the same `PUT`, the same `tokenSha256`).
- A deploy key or a person's token on the runner machine stays possible, and is no longer needed. A fetch without a credential keeps the runner's own git setup.

Libraries: none new. The App's installation tokens (`worker/github/Tokens.ts`), git's own `GIT_CONFIG_*` environment.
