# Work links

What links an issue to the work on it: who works on it, their lane or agent session, the merge-queue entry, the pull request, the merge and the review. Whoever does the work posts the links; the issue's status follows them, and no person edits it ([decision 0147](../decisions/0147-work-links.md)).

## How it works

```
a lane, the merge queue, a reviewer                  ChatApi                               every device
  ops/work-links/link.mjs ── POST .../issues/<n>/links ──▶ a Member, a run credential, or
     Bearer <runner token>                                 a runner on the repository
                                                           upsert work_links (newer `at` wins)
                                                                 │
  smthrs issue list, the proof ◀── GET .../issues?work=pr-or-queue (status + links per issue)
                                                                 └──▶ Electric /api/shapes/work-links ──▶ list chips, issue page sections
```

### TODOs made from an issue

A TODO made from an issue links its own work there, with no post: the stack's writer (`worker/stack/Stack.ts`, `linkWork`), in the same transaction as each change to the TODO, writes its links with `source` `todo:<number>`. The TODO itself is a `session` link, `TODO #<n>` (`working`, `done` once merged, `closed` once dropped, `failed`; no state while queued or in review); its pull request a `pr` link, `#<p>` to GitHub (`open`, `merged`, `closed`); and once merged, its merge commit a `merge` link (`merged`). So an issue a TODO took to a merged pull request reads Merged, with the TODO, the pull request and the merge one click away. No one else may post as `todo:<n>`: it is the server's own write, not a route.

## Our own work: the lane helper and the importer

Our lanes track their work as issues on the public repositories smithersai/vibelang and smithersai/smithers, as a tree under **Ship VibeLang** on smithersai/vibelang (`ops/issues/tree.mjs`), filed as GitHub sub-issues.

```sh
node ops/issues/track.mjs open    --repo smithersai/vibelang --title "<title>" --body-file <f> --key fuzz:<id> --label migrate:alchemy --parent smithersai/vibelang#<N> --dry-run
node ops/issues/track.mjs link    --repo smithersai/vibelang --issue <N> --kind lane --ref <lane> --state working
node ops/issues/track.mjs comment --repo smithersai/vibelang --issue <N> --body-file <f>
node ops/issues/track.mjs parent  --repo smithersai/smithers --issue <N> --parent smithersai/vibelang#<M>
node ops/issues/track.mjs update  --repo smithersai/vibelang --issue <N> --state closed
node ops/issues/track.mjs retry   --repo smithersai/vibelang --write <id>
```

- **Who writes.** A [machine token](machine-tokens.md) per repository, from the file `$SMITHERS_ISSUE_TOKENS` names, JSON `{ "<o/n>": { "file": "<token file>", "agent": "<agent>", "lane": "<lane>" } }`, with the agent and lane the token was issued to. The map and each token file must be mode 600, and a token file holds one whole `smm_` token. Write ids are scoped to the agent and lane, so a lane's new token retries its same writes. The App's bot is the author. `--dry-run` sends nothing and prints each request with the token named, not shown.
- **Reuse.** `open` reads the repository's issues shape and reuses an issue, open or closed, whose body has the same `key: <kind>:<id>` line; a same-title issue is never a receipt for a keyed issue. Otherwise it submits a machine write whose id comes from the key, so a command run again is the same write, and watches it settle. Without a key, a lane opening an issue on purpose reuses an open issue of the same normalized title.
- **Public content.** Everything sent goes through `ops/issues/scrub.mjs`: it redacts credentials, absolute home and machine paths (never a repository-relative path or a `name@version` file), machine names, account names, emails and private repository names (passed at run time, never committed), and fails closed, exit 2, on a title, label or ref that needs a redaction.
- **Sub-issues.** GitHub's, through `issue/relate`: 100 children per parent, eight levels, the same owner (any repository of it). The server looks first: already there is done, and another parent is refused, never replaced.
- **Pacing.** The server's: every GitHub mutation waits for a send slot ([machine tokens](machine-tokens.md#pacing)).
- **Filing a plan.** The repository flow `issues/file-tree` (`.smithers/flows/issues/file-tree/`) files the importer's plan: `SMITHERS_ISSUE_TOKENS=<tokens.json> smthrs flow start issues/file-tree --data '{"plan":"<plan.jsonl>","acceptDropped":<n>}' --wait`, and `smthrs runs resume <run>` after a stop; run state is in `.flows/`. It refuses a plan with unacknowledged dropped rows, a depth past 8, a node past 100 children, another owner, an unknown parent or a dead token. Then, row by row in the plan's order (the tree, then drafts, then findings, then queue work links), it submits the create, watches it, submits the sub-issue, watches it, and posts the work links. Each attempt is one recorded action that never waits or retries, and the run sleeps on the engine's durable timer between them.
- **The importer.** `node ops/issues/import.mjs --out <plan.jsonl> [--draft <source>=<file>]...` reads the open spec-review and scoped-review findings and the example-repository migration findings on the lane host (read-only), main's pending fuzz gaps, and the agents' drafts; deduplicates by key and title; scrubs; places each in the tree; and writes a mode-600 plan with every dropped record and why. A merge-queue entry is work, not a problem, so it files no issue: an open entry naming an issue (`issues`) becomes a `queue` work link in the plan, and one naming none goes to `<plan>.queue-unlinked.jsonl` until TODO leaves can hold it. It posts nothing. Those sources use the operator's own `ssh` and `gh` logins; `--source lane-host|fuzz` selects some of them. A filed sub-issue cannot move to another parent, so placement is stable: each node keeps 10 of its 100 places for part nodes, a new record takes the first free direct place, then an open part, then a new part, and `--previous <last plan.jsonl>` keeps every issue the last plan placed under its parent there. Plan every import after the first with `--previous`. A node whose 100 places are all filed refuses a new record by key rather than moving filed ones.
- **Filing state.** The cursor keeps node numbers only while an unprocessed row can still name them as a parent. Completed leaf receipts stay in the journal; recording `forgetNodes` on the action outcome keeps that cleanup replayable, including after a retry. Needed failed parents remain `null`, so their children still report the missing parent.

- **Draft mode.** An agent plans its own drafts with the App alone: `node ops/issues/import.mjs --out <plan.jsonl> --draft <source>=<local file>... --private-repos <file>` (or `SMITHERS_PRIVATE_REPOS_FILE`), with no `--source`. It reads only the named files, runs no `gh` and no `ssh`, and plans them with the whole tree; `issues/file-tree` then reuses existing nodes and issues by their `key:` marker through smithers.sh's public issue shape. It refuses a `host:path` draft, which needs ssh, and a run with no private repository names, since the scrub would miss them. It reads no existing issues itself: `GET /api/repos/<owner>/<name>/issues` takes a session or a runner's token, and a machine token reads there as signed out.

- **Repository confirmation.** In either importer mode, every `owner/name` or `github.com` repository reference in drafts and plan rows is denied until `GET https://api.github.com/repos/<owner>/<name>` returns `200` with `private: false`, read anonymously or, for the owner its scope receipt covers, with the App read token that `SMITHERS_GITHUB_READ_TOKEN_FILE` names (`ops/issues/githubRead.mjs`). An anonymous request sends a User-Agent and no token, omits credentials and refuses redirects; neither runs `gh` or `ssh`. At most 60 anonymous and 500 App-token requests are sent per run. Discovery and the scrub share one pipeline over readings that keep source offsets (`ops/issues/reading.mjs`): the text as written, each decoding round (with NFKC and with original glyphs preserved, so compatibility normalization cannot erase owner look-alikes before another escape decodes; percent escapes, the full HTML5 named-entity table (an unknown name stays literal), numeric references, invisible characters, Markdown escapes), the same with combining marks (other than the slash overlays) dropped and with Markdown emphasis markers and HTML tags dropped, and each normalized form, in which every code point named SOLIDUS or SLASH, their look-alikes and every one NFKC folds to a slash read as `/` (`reading-data.mjs`, generated from Unicode data by `reading-data.py`), colon-likes read as `:`, whitespace and controls around a slash between two name characters go, slash runs are one `/`, and `.` and `..` steps are resolved and also dropped. Every token of every reading is read for a URL's repository (Pages included: `<owner>.github.io/<name>` names `<owner>/<name>`), for a bare pair outside the prose rules that starts a path (dotted names and path suffixes included), for every other pair in a repository's path, query keys and values and fragment, for GitHub's cross-repository `owner:name` in a compare spec or a `head`/`base` parameter (`/compare/main...owner:name:branch`), and anywhere for a pair under a watched owner. Watched owners are a fixed set (smithersai, roninjin10, codeplanesmithers, williamcory, fucory, tevm, evmts, dtechvision; the App's installation owners are among them), each line of an optional `--watched-owners <file>`, the targets' owners, the private list's owners, and every owner named by a non-bare primary reference anywhere in the run: code-host URLs (including scp `<github-host>:owner/name`), owner-only GitHub URLs, Pages, compare/cross references and repository fields. Credential-bearing fields contribute only complete safe URL owners; they never contribute repository lookups. Owner comparison folds Cyrillic and Greek look-alikes and recognizes word, digit and hyphen glue before a watched owner. Untied slash pairs outside the explicit prose rules in `ops/issues/prose-data.mjs` require confirmation; a 404 or unconfirmed verdict redacts them. Prose alternatives, branch prefixes, scopes and file paths retain their zero-request behavior. Bare colon candidates are redacted without lookup; explicit cross references, scp and URLs retain confirmation. Curl and wget user operands carry credential roles in command option data. Only the path's own structure is exempt: the repository name joined to its next segment, a route to its ref or number, a common ref to its first directory, and a file path after a path root (`docs/`, `src/`…). Every name the private list holds is private under any owner or path root, and an `owner/name` entry makes `owner` a watched owner everywhere. Inside a public repository's file path after a path root (`blob/main/docs/<owner>/<name>`), only watched owners and listed names are read: an unwatched owner's private repository named there is not caught, a gap accepted in review so that deep file links into public repositories survive. To close it for an owner, list one of its repositories as `owner/name`. GitHub's cross-repository `owner:name[:ref]` is read after `compare/`, `..`, `...`, `?`, `#`, `&`, `=`, a `tree/`, `blob/` or `commit/` route, or `head`/`base`, in bare text as in URLs, and under a watched owner anywhere. Each reference nothing confirms is redacted by its source span (a URL's token, a bare path, or a pair), on the whole field, never by whitespace token. A second, form-free layer searches every reading for each known private name as text bounded by non-word characters and redacts its span: every `--private-repos` entry as `owner/name` or `owner:name` and, when distinctive (at least 4 characters with a hyphen, underscore or digit, or at least 10 characters), as the bare name; and every pair the run learned private (a 404 or `private: true`), under any owner, as `owner/name` or `owner:name`. Qualified private names use only the name’s word boundary; punctuation suffixes and text glued before the owner cannot hide them. Public and unconfirmed names do not enter this layer. The run carries repository verdicts and watched owners as explicit fields, so copying the verdict map does not drop run metadata. Anything either layer still finds in any reading of the result refuses the field. With both layers, a leak needs a private name the run does not know, not a spelling nobody thought of. A bare `owner:name` with no compare or head context, under an unwatched owner, is not read. Nested names are requested only once a repository around them is public. Case variants, URLs and decoded references share one verdict per run. Prose periods and ellipses do not hide following references. Discovery reads original source fields before clipping can erase credential context; transformed fragments cannot trigger new lookups. Complete `repo` destination values require their own verdict, including trailing dots. Private overrides use the same case and `.git` normalization as discovered references. Trailing dots in repository URL paths are retained, and complete URL fields never lose punctuation before validation. Each draft or operator finding is parsed without title/body formatting, validated independently, then formatted; rejected originals retain their deduplication position. Safe findings survive alongside rejected or closed findings, and redactable body paths are scrubbed. Both written repository paths and normalized URL destinations require public verdicts. Line-level URL readings prevent the next source line from changing a repository name. URL candidates are recognized before their host is normalized, including Unicode host spellings and protocol-relative authorities; external hosts grant no GitHub repository verdict. Whole GitHub URLs are normalized before lookup, including dot segments, encoded dots, ports (including empty ports) and backslashes; a public prefix cannot authorize another destination, and embedded hostnames never truncate the primary URL. Tab, CR and LF are removed in an additional URL reading before verification. Every containing source/token, decoded and control-normalized reading and final repository name is screened for credentials before substring extraction, requests or reports; an encoded credential prefix cannot leave its payload looking like a repository owner. URL fields are parsed as complete values, including literal spaces; GitHub API `/repos/<owner>/<name>` URLs resolve to that repository. Known raw/codeload hosts use their repository paths; unknown GitHub subdomains fail closed. Credential-bearing fields are opaque to repository candidate discovery: their original decoded readings are screened before any redaction, and no substring from them is requested or reported. Credential-named properties (including decoded names) make their entire value/subtree opaque and are refused in publishable rows. Private-key blocks are opaque before any prefix redaction. Property names are checked too, and diagnostics use fixed names or indices. Filing markers are added after source validation, using already-checked keys and labels. `404` means private; other statuses, invalid responses and network failures mean unconfirmed. After `403` or `429`, no more requests are sent and all unasked names remain unconfirmed. Both private and unconfirmed references are scrubbed; titles, labels, refs, keys and destinations needing redaction drop the row. Generated nodes are checked, and children of dropped nodes are dropped too. An unconfirmed root leaves an unfileable plan. Ambiguous bare slash-separated text is checked conservatively as a repository reference.
- **Inspect before filing.** The importer's printed JSON and plan summary include `repositories: [{ repo, verdict, reason }]`; the same list is saved as mode-600 `<out>.repos.json`, for example `plan.jsonl.repos.json`. It includes references from closed and duplicate drafts too. The sidecar and summary may name private repositories: keep them out of public content. Dropped and duplicate rows use opaque identifiers and fixed rule/field diagnostics, never rejected source content. Unlinked queue entries are screened too; rejected entries retain only an opaque ID and problems. With no private list, the importer plans nothing.

## Routes

| Route | Answers |
|---|---|
| `POST /api/repos/<owner>/<name>/issues/<number>/links` | `{ links: [{ kind, ref, label?, url?, state?, at? }] }`, 1 to 50 links: `200 { links, changed }`. `kind` is `assignee`, `session`, `queue`, `pr`, `merge` or `review`; `state` `working`, `queued`, `open`, `passed`, `failed`, `merged`, `done` or `closed`; `url` `https` only; `at` UTC ISO 8601, at most 5 minutes ahead, else the server's time. A link already there changes for a newer `at`, even with the same state (a lane working again after its queue entry failed is the newest word); the same `at` changes it only when something differs, so a post sent again changes nothing. The client sets `at` once per post. Who: a Member or above (session or run credential), or `Authorization: Bearer <token>` of a runner registered on the repository through its Admin role, with the App's installation recorded (`source` `runner:<name>`; decision 0148). `400 invalid`, `401 authentication`, `403 forbidden`, `403 not_authorized` (a runner that needs [registering again](agent-runners.md#registering-a-runner-again)), `404 not_found`, `405`, `413 too_large`, `429`/`503` from the role check with `retry-after`, `503 unavailable`. One `work.links` log line and span and one `smithers_work_link_posts` count by `outcome` and `by`; never a ref, label or URL |
| `GET /api/repos/<owner>/<name>/issues` | each issue has `work: { status, links }`; `?work=pr-or-queue` keeps issues with a `pr` or `queue` link, `?work=any` issues with any link. A runner's token reads it too, on the same terms as a post ([issues](issues.md#routes)) |
| `GET /api/shapes/work-links?repo=<owner>/<name>` | the repository's `work_links` with `WORK_LINK_COLUMNS`, read as the issue shapes are |

## Status

`workStatusOf` in `src/features/issues/work.ts`: `merged` once any link merged; otherwise the latest link with a state other than `closed` decides: `working` Working, `queued` Queued to merge, `open` In review, `passed` Passed the queue, `failed` Failed, `done` Done; none: No work linked.

## The browser

- **The list** (`/$owner/$repo/issues`): each row's status chip, and its pull request, queue entry and merge when their links have a URL. The Work tabs: Any, and **Linked to a PR or queued merge** (`?work=pr-or-queue`), combinable with search, sort and the schedule.
- **The issue page**: a Work section with the status, then one section per kind (Working on it, Session, Queue entry, Pull request, Merge, Review), each link one click when it has a URL, with its state.

## Posting links: the client

`ops/work-links/link.mjs`, no dependencies. Register a runner on the repository for the poster first ([runners](agent-runners.md#setting-it-up)); its token is the poster's. A runner token posts and reads only while its runner is current as a claim requires: registered through the repository's Admin role, with the App's installation recorded ([decision 0148](../decisions/0148-runner-git-credential.md)). Otherwise a post is `403 not_authorized` and the script exits 1 with `work link refused: HTTP 403 not_authorized`: [register the runner again](agent-runners.md#registering-a-runner-again).

```sh
node ops/work-links/link.mjs --repo acme/widgets --issue 12 --kind session --ref lane:fix-12 --state working
node ops/work-links/link.mjs --repo acme/widgets --issue 12 --kind queue --ref 1793580204-fix-12 --state queued
node ops/work-links/link.mjs --repo acme/widgets --issue 12 --kind pr --ref 41 --state open --url https://github.com/acme/widgets/pull/41
node ops/work-links/link.mjs --repo acme/widgets --issue 12 --kind merge --ref 5e0fdb74 --state merged --url https://github.com/acme/widgets/commit/5e0fdb74
```

The token comes from `--token-file`, `$SMITHERS_WORK_TOKEN_FILE` or `~/.smithers/runner/runner-token`, never argv. After trimming the file, it must hold one nonempty token containing only printable ASCII characters without spaces. An invalid token exits `1` with `invalid runner token` before constructing a header; a transport or header failure exits `1` with `work link request failed`. Neither diagnostic includes the token or the underlying error. With curl: `curl -H "authorization: Bearer $(cat <file>)" -H 'content-type: application/json' -d '{"links":[...]}' https://smithers.sh/api/repos/<o>/<n>/issues/<n>/links`.

## The proof

One command proves on a deployment that Smithers tracks our issues: `E2E_PROD_URL=https://smithers.sh node e2e/prod.mjs e2e/issue-tracking.spec.ts --project=deployment`. It needs a PRIVATE repository the test account administers, with the App on it, named in the run's `e2e.env` with the import's files (need `trackingRepository`); the records hold private paths, so never a public one.

1. **Collect**, at run time, never committed: `node ops/issue-tracking/collect.mjs` reads the proxy inbox and, on the lane host, every lane's prompt, start and exit, its review report and each merge-queue entry, scrubs anything credential-shaped, and writes one issue record each, with the links it implies, to a mode-600 file.
2. **Seed**: `node ops/issue-tracking/seed.mjs --repo <owner>/<name>` creates them through Smithers' own writes route as the test person, one every 7.5 s (480 an hour, under GitHub's 500 content creations an hour), resumable, waiting out `retry-after`, and pausing while a production e2e run holds `run.lock`. It counts a record seeded only when its write is `done`: it watches each admitted write until it settles, ends `unsettled` with exit code 1 while any is pending, failed or refused, names each failed one, and a rerun watches and reports them again. 5,000 issues take about 10.5 hours.
3. **Prove**: (a) the paged list walks every issue and the browser lists, searches and opens one within budgets; (b) every seeded record is an issue with its title; (c) a registered runner posts each record's links, the list and its `?work=pr-or-queue` filter answer them, and from a lane's issue one click reaches its lane, session, queue entry and merge; (d) a new issue's status follows a machine's posts, live on its page. Numbers go to `test-results/issue-tracking.json`.

**The cold waterfall**: `E2E_PROD_URL=https://smithers.sh node e2e/prod.mjs e2e/issue-waterfall.spec.ts --project=deployment` opens the list and one issue on new devices (`E2E_WATERFALL_VISITS`, 3 by default) and prints each visit's stages: the document, the app's assets, the boot's marks, every `/api/` request and the main thread's long tasks, until the first rows or the issue's title showed. `E2E_WATERFALL_PROFILE=<dir>` saves each visit's CPU profile. Paths name the repository `<repo>`; no title or body leaves the browser.

Settings: `E2E_TRACKING_REPOSITORY`, `E2E_TRACKING_RECORDS`, `E2E_TRACKING_SEED_STATE`, `E2E_TRACKING_RUNNER_TOKEN_FILE` (made and registered by the spec when absent), `E2E_TRACKING_MIN_ISSUES`, `E2E_TRACKING_LINKED`.

A person's session is decided after complete body admission; natural expiry or explicit revocation during a bounded
wait is accepted without another per-route session check. Repository-role resolution has a 10 s whole-service budget
including GitHub; runner token lookup instead has 2 s. The complete writing call, including database acquisition, has
6 s: totals are 16 s for a person or 8 s for a runner. The transaction also keeps its Postgres 5 s cap (lock 1 s,
statement 2 s). Timeout stages emit `write.wait` and `smithers_write_wait_timeouts`.
See [the wait inventory and transport limits](../work/commit-authority.md#astra-repair-5--every-synchronous-wait).

Tree destinations, repeatable `--repo owner/name` confirmation targets and explicit draft `repo` fields are requested before prose. Bare repository names obey the 100-character limit after `.git` normalization. Query expressions such as `repo:owner/name` are scanned as well as slash-delimited paths. A run sends at most 60 anonymous requests. Public `private:false` responses alone are cached for 24 hours in `~/.cache/smithers/public-repos.json`, mode 600. `repositoryRequests` and `unconfirmedRepositories` in the private summary show the count and every unconfirmed name. After checking those names, an operator can supply `--public-repos <file>`: a caller-owned mode-600 regular file with one exact `owner/name` per line. Private overrides win; explicit public grants are never persisted in the response cache.

Repository ties come from command argument structure, host routes and configuration values. Any `owner/name` argument in a `gh` command ties its owner, including quoted arguments, `-R`, `--repo`, `--repo=`, and `gh api repos/owner/name`; the same argument rule covers GitHub package/install tools, including options before their subcommands. Quoting (ordinary, locale and ANSI-C strings), escapes, comments, grouping, substitutions and command separators determine argument boundaries before path normalization; composed command words retain their decoded identity and source ranges, while ordinary prose backslashes retain path meaning; ordinary words are valid argument values. Executable basenames may be quoted, escaped or reached through a path. Complete command and configuration values retain exact repository identities, including terminal dots. Repository-valued command field assignments contribute ties after option and nested field parsing, with compatibility syntax normalized independently of values; every field key is screened for credentials before discovery. Dependency package names retain their object or indented-map context and cannot become credential labels. Serialized JSON keys and values use JSON string decoding, with each text field retaining its own grammar context and enclosing dependency or credential context, including containers inside shell quotes. Enclosing comments suppress grammatical ties through decoding while explicit URL references keep their privacy meaning. JSON and ANSI-C escape notation cannot fabricate a second repository identity. Decoded units retain exclusive source ranges, preserving adjacent punctuation and credential exclusions. Standalone dependency snippets and visually wrapped repository arguments retain their meaning; ordinary JSON text fields remain prose. Named npm-style arguments, including scoped names, retain their complete repository spec; an ordinary registry scope remains untied. Package-name prefixes are interpreted only in dependency-command context, as in [npm package argument parsing](https://github.com/npm/npm-package-arg/blob/main/lib/npa.js). Physical shell continuations keep one semantic identity across lines; visual argument wrapping cannot cross blank or comment-only lines. A shared command-argument parser uses declarative option roles from typed GitHub CLI flag metadata (gh 2.94.0), including command-specific boolean clusters and detached operands. Unknown short flags retain all possible owner-shaped operands conservatively and cannot grant a guessed public identity. Attached short-option prefixes are parsed syntax: their source-mapped operands retain exact public identities through quoting and encoding, without masking nested references. YAML node properties and sequence mappings retain dependency scope without absorbing sibling fields. Quoted YAML keys and scalars decode their own escape and folding grammar with source spans before identity or credential classification, including block values; malformed quoted values remain unconfirmable. Quoted dependency specifications and parsed dependency containers (with or without refs), `GH_REPO`, `GITHUB_REPOSITORY`, `github:` and Actions `uses:` entries contribute ties too. See the [CLI repository option](https://cli.github.com/manual/gh_pr) and [repository environment variable](https://cli.github.com/manual/gh_help_environment).

The reserved top-level route table skips GitHub application names when locating an owner; `codespaces/new/owner/name` skips both route segments. Profile `@owner`, `u/owner`, `.png`, `.keys`, `.gpg` and `.atom` forms tie the same account. Every GitHub host reads decoded `user:`, `org:`, `owner:` and `repo:` qualifiers across every URL component, including negation and form-decoded spaces, before malformed-authority exits. Credential payloads remain excluded. SSH aliases shaped `github.com-<alias>` are GitHub hosts. Valid SCP paths tie only their owner. Bracketed DNS authorities and malformed GitHub ports are classified before normalization and stay unconfirmable. A malformed GitHub authority contributes every complete owner-shaped segment after its host, split on slash and colon, excluding numeric ports by authority position through repeated colons and trailing punctuation, and excluding prose words, while retaining numeric path owners; it never grants a public verdict. Registry paths use their namespace position, including `ghcr.io/v2/owner/name` and `npm.pkg.github.com/@owner/name`.
