# smithers.sh browser canary

Owner: Smithers release operator. The [Canary workflow](../../../.github/workflows/canary.yml) runs from `smithersai/smithers` against `https://smithers.sh`. After qualification, set the repository variable `CANARY_ENABLED=true` to enable scheduled and post-deploy probes. Until then, only explicit manual dispatch runs. Every quarter hour the enabled workflow checks uptime; hourly and after deployment it also launches Chromium. A failed probe creates or updates the fixed `Canary: smithers.sh is failing` issue, then makes the job red. Only a complete browser-and-uptime pass comments and closes the issue; a quarter-hour uptime pass leaves an existing alert open for the next full run.

Configure `CANARY_SESSION_COOKIE` as a valid ordinary non-admin test session cookie header, `CANARY_SESSION_LOGIN` as that login, `CANARY_BROWSER_REPO` as a private fixture repository owned by that account, `CANARY_BROWSER_WORKSPACE` as the existing fixture workspace UUID, and `CANARY_BROWSER_FLOW` as a configured, safe, input-free flow in that workspace which runs long enough to observe a running state (at least 20 seconds) and completes without approval or repository mutation. Keep this fixture available. The saved `codeplanesmithers` account currently has admin privileges and is useful for diagnosis, but cannot qualify this scheduled canary; both browser and uptime checks require ordinary permissions. The browser probe fails if the cookie, workspace, or flow is missing; it never silently skips signed-in coverage. Rotate the cookie when the session expires. The workflow target is pinned to the apex, so a repository variable cannot redirect its browser to a preview host.

The fresh context proves signed-out boot and editable Chat. A separate isolated context receives only the scoped cookie, verifies the account, selects the fixture workspace, renders the Files browse, opens setup, and holds the actual workflow launch response while checking Chat. It releases that response, records the accepted run ID, checks Chat during execution, and requires a completed remote projection and rendered run receipt. Its `canary-browser` artifact contains screenshots and `result.json`, including the run ID but no cookie. No persistent profile is involved in scheduled runs.

On alert, inspect the Actions run and its `canary-browser` and `canary-uptime-report` artifacts. Check the accepted run ID and terminal projection before retrying a run; an ambiguous launch may already have created a job. Restore the fixture or session if configuration failed, then rerun the workflow. A healthy rerun closes the issue. The release operator owns triage and escalation through the repository's issue notification settings. This issue route is **not proven to notify an operator** until the drill below records an actual receipt from a watched account.

For the delivery drill, dispatch **Canary** with `force_browser_failure: true` against the deployed workflow. The browser completes its real run before deliberately failing; verify a red run, the browser artifact and failure check in the issue body, and receipt of the GitHub issue notification by the designated release operator. Record the run URL, issue URL, recipient and notification receipt time. Dispatch again with the flag false and verify the issue closes. Do not infer notification delivery merely from issue creation. After both manual runs and the notification receipt pass, set `CANARY_ENABLED=true` and record a successful scheduled execution. Keep the operator's watched-issue notification enabled; if nobody receives it, configure a monitored channel and repeat the drill before treating B09 as closed.
